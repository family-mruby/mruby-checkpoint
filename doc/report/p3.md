# P3 報告: 試験一式をランダムなセーフポイントで往復させる

> 状態: 実装済・検収待ち (Fiber・Task は止まる条件に当たったので、案を書いて返す) | 更新: 2026-11-03 | 指示は `doc/instruction_p3.md`

## 結果

- mruby 付属の試験一式 (中核の `test/t/*.rb` 43 本と、このビルドの gem の試験 59 本、計 102
  ファイル) を、プログラムの協力なしに外から止め、イメージを書き、新しい `mrb_state` (と、10 個に
  1 つは別のプロセス。32bit と 64bit に交互) に復元し、古い状態を捨てて続けた。
- 長い版 (シード 1〜20、1 ファイル約 200 点): 2,040 回の実行、試みた点 407,260、書けたイメージ
  370,639。**往復なしと食い違った実行は 0**。除外の表 (`test/fuzz_exclude.txt`) の 3 つの
  試験で、正当な違い (アドレス由来の値、プロセスの資源) が 17 回あった。
- 途中で見つけた食い違い・落ちる場面は 20 件。すべて原因を調べて直した (§見つけた食い違い)。
  そのうち 6 件は P1 からの不具合 (基準の控えの指し先の崩れ、cfunc の Proc の引数の仕様、
  別名の Proc、行番号ほか)。
- 方針 (2026-11-03 の追加の指示: 断るより運ぶ) に沿って、運べなかったもの 20 種ほどを運べる
  ようにした (bigint・Struct・Set・Rational・Complex・Random・prepend・Time・Regexp・
  MatchData ほか。§新しく運べるもの)。いま断るのは、原理的に運べないもの (C の関数のフレーム、
  プロセスの資源) と、形式の作り直しが要る Fiber・Task だけ。
- 死んだレジスタの計算を書き出しに入れた。イメージ 1 つあたり平均 1.22 個のレジスタを nil にし、
  同じ点で比べると、断った点の 3.7% (Fiber・IO などを古いレジスタが指していたもの) が書ける
  ようになった。
- SabiRuby で試験一式の一部 (中核の試験 37 本 × 20 点) を続けた: 740 点のうち C で書けた
  729、SabiRuby で断った 13 (未対応の種類を理由つきで)、続いた 716 は**すべて往復なしと一致**。
- `rake test` に短い版 (シード 1、約 30 点、約 3,000 点、数秒) を足した。長い版は
  `rake fuzz[seed,runs,points]`、SabiRuby は `rake fuzz:sabiruby[seed,points]`。
- 普段のビルドの `vm.c` の patch は変えていない (外からの停止は試験のビルドだけの道具が
  既存のセーフポイントに要求を出す形)。そのため valgrind の命令数の比較はしていない。

## 外からの停止の方式

**既存のセーフポイントに、外から要求を出す**。止める点を数えるのは試験のビルドだけの道具で、
書き出すのは普段のビルドと同じ道 (P1 の `task.switching` への相乗りと hook)。

1. 試験のビルドの `checkpoint-fuzz` は、VM の命令ごとの hook (`code_fetch_hook`。
   `MRB_USE_DEBUG_HOOK`、mrdb が使うもの) で取り出した命令を数える。シードから決めた数 (前の点
   から 1〜2×平均の一様乱数) に達したら、`mrb_checkpoint_request()` を呼ぶ。
2. `mrb_checkpoint_request()` (gem の API、普段のビルドにもある) は、その場で運べない理由が
   あれば返す (Fiber・Task の中、C の関数が呼んだブロックの中、Task がある、前の要求が
   まだ待っている)。無ければ `save` と同じくフラグを立て `task.switching` を立てる。
3. VM は次の命令の境目 (= P1 のセーフポイントの条件を満たす最初の境目) で hook を呼び、gem が
   書き出す。断る理由が出れば (運べない型など)、例外を上げずに報告の関数へ渡して続ける。
   いちばん上のフレームのレジスタは書き換えない (`:resumed` は入らない)。
4. 道具はイメージを受け取ると、新しい `mrb_state` へその場で復元してみる。復元できなければ
   「復元で断った」として古い状態のまま続ける。できれば、次の命令を取り出す直前 (何も
   実行していない) に `longjmp` で古い VM を抜け、古い状態を閉じ、新しい状態で
   `mrb_checkpoint_continue()` する。10 個に 1 つは、イメージをファイルに書いて別のプロセス
   (`--peer` の 32bit 版と 64bit 版に交互) を起こし、そちらが同じ数え方を引き継いで続ける。

選んだ理由:

- 止める点を外から決めるのに、VM に手を入れずに済む (命令ごとの hook は試験のビルドで
  有効にし、道具が state ごとに付ける)。普段のビルドの `vm.c` の patch は P1 のまま。
- 書き出しは本番と同じ道を通る。外からの要求 (割り込み・別のスレッドのフラグ) は Family mruby
  に持ち込むときにも同じ API で済む。
- 再現できる: 点は「何個目の命令を取り出したときに要求したか」(全状態・全プロセスを
  通した数) で決まる。同じシードで同じ点になり、`--at N,M,...` でその点だけを要求できる。
  食い違いが出たら、`tools/fuzz.rb --isolate` が 1 点ずつ・最短の組み合わせを探して書く。
- 比べた案: 命令の hook の中で直接書き出す。セーフポイントの判定 (C の境目・例外の途中) を道具が
  持つことになり、本番の道を試さない。

要求から書き出しまでの間 (要求した命令の実行中) に、例外が飛び始めた・C の関数が呼んだ
ブロックへ入った場合、VM は書き出しを先送りし、条件がそろった最初の境目で書く。要求は
断らない (P1 の hook の条件のまま)。Fiber へ入ってしまった場合だけは、そのまま進めると
Fiber の VM がスケジューラへ戻ってしまうので、断る (「要求の後に Fiber へ」84 回)。

古い状態を捨てるとき、`mrb_open` の後に登録された終了の処理 (試験の補助やプログラムの
もの) は走らせない。プログラムは別の状態で続いているので。

## 死んだレジスタの計算

`checkpoint_live.c`。書き出す瞬間に、各フレームの irep の命令列を後ろ向きのデータフローで
解析し、フレームの pc で生きているレジスタを求める。読まれない一時レジスタは nil で書く。

- 命令ごとに読むレジスタと必ず書くレジスタを表にした (`ops.h` の 119 命令)。読み方が
  はっきりしない命令 (`ENTER`・`ARGARY`・`BLKPUSH`・`KARG`・`KEY_P`・`KEYEND`・`CALL`) は
  全部を読むとみなす。書く方は確かなときだけ数える。外れるなら必ず「生きている」側。
- 流れ: 次の命令、飛び先、例外処理の表 (命令の終わりの位置が範囲に入る処理の飛び先。
  `catch_handler_find` の `begin < pc <= end`)、`RAISEIF` からは ensure を通る jump の
  全部の飛び先 (`JMPUW` の続き)。
- いちばん上のフレームは次に実行する命令、下のフレームは呼び出しの次の命令で見る。下のフレームでは、
  呼び出しから例外が来たときの処理の飛び先も足す。
- 判断しないもの (常に書く): R0 と引数のレジスタ (`ci->n`・`ci->nk` から求めるブロックの
  位置まで)、ローカル変数 (`nlocals` 未満。Env・`binding`・`eval` が名前で読める)、まだ最初の
  命令を実行していないフレーム (pc 0。`ENTER` が呼んだ側の並びで引数を読む)、いちばん上のフレームの
  `nregs` より上。
- スタックの 1 つの位置は、そこを窓に含むどれかのフレームが生きているとすれば書く (呼ばれた側
  の R0 は呼んだ側の R[a])。

結果 (5 つの種 × 200 点、同じ点で比べた):

| | 死んだレジスタを nil | そのまま (`--keep-dead`) |
|---|---:|---:|
| 試みた点 | 101,703 | 101,655 |
| 書けたイメージ | 92,517 | 92,113 |
| 断った | 9,186 | 9,542 |
| うち Fiber の値 | 1,869 | 1,998 |
| うち Task::Queue | 352 | 405 |
| うち資源 (IO・UDPSocket・File・Dir・Socket) | 2,340 (784・769・369・318・100) | 2,514 (817・823・372・396・106) |
| イメージの平均の大きさ | 34,759 B | 34,802 B |
| nil にしたレジスタ (nil 以外の値だったもの) | 1.22 個 / イメージ | 0 |

断った点の 3.7% (356 点) は、もう読まれない一時レジスタに Fiber・IO・Dir などが残って
いたのが理由だった。食い違いは両方とも 0。

P2 の「SabiRuby に無いものを古いレジスタが指していて断った」場面: 中核の試験の SabiRuby の
部分 (740 点) では、計算の有無で数は変わらなかった (どちらも SabiRuby で断ったのは 13 で、
理由は未対応の種類だけ)。P2 で当たった `builtin_patch` の場面 (C の関数が作った内部の
Array) は、P2 で素のクラスを当てて直してあり、そもそも断らない。

## 試験一式の流し方

- 1 ファイルずつ、mrbtest の `assert.rb` + 試験のファイル + `report` を 1 つのプログラムに
  して流す。状態は mrbtest と同じ準備 (`t_print`・`_str_match?`・`Mrbtest`・`GEMNAME`・
  `$mrbtest_verbose`・gem の C の試験の補助) をしてから基準を取る。mrbtest と違い、gem の
  試験も全部の gem を入れた状態で流す (書く側と読む側の基準をそろえるため)。
- 比べるのは、往復なしの実行 (同じ道具の `--ref`) との出力 (試験の名前と結果が 1 行ずつ
  出る verbose の形と、最後の数) と終了の状態。`report` の経過時間の行と、mkstemp の
  ランダムなファイル名 (mruby-io の試験が失敗の文言に出す) だけ比べない。往復なしでも
  毎回変わるもので、復元とは関係ない。
- 1 ファイルの点の数は、往復なしの命令数 / 点の数 を平均の間隔にして決める。

- **キーの `hash` / `eql?` の副作用**: 復元は Hash と Set を入れ直すので、キーが利用者の
  `hash` / `eql?` を持てばそれが走る (CRuby の Marshal.load と同じ)。`hash.rb` は、呼ばれると
  Hash を空にするキー (`HashKey` の callback) を使う。入れ直しの途中で例外が出たか、Hash の
  大きさが変わったら、復元を断る (道具は古い状態で続ける)。キーの hash の値をイメージに持たせれば
  呼ばずに済むが、mruby の Hash はキーの hash の値を持っていない (VM の変更になる)。
- **ObjectSpace だけの permanent**: VM を開いた直後からある Proc を、プログラムが
  `ObjectSpace.each_object` で拾ったもの (mrblib の中のブロックなど)。定数・メソッド表から
  たどれないので、相手側で同じものを指す名前が無い。

## 止まる条件: Fiber と Task

断った点の 52% (18,901 / 36,621) は Fiber・Task に関わる。「断るより運ぶ」の方針で直そうと
すると、次の 2 つが要る。どちらも指示書の止まる条件 (形式・セーフポイントの条件の作り直し) に
当たるので、実装せずに案を書く。

1. **形式にコンテキストを足す**。いまの VM の部分はルートのコンテキスト 1 つ (スタックとフレーム)。Fiber の
   オブジェクトを運ぶには、コンテキストごとのスタック・フレーム・状態 (未開始・中断中・
   実行中)・どのコンテキストから resume されたか (`prev`) を持つ表が要る。Env の「スタック上」
   も、どのコンテキストのスタックかを持つ (いまは ROOT に決め打ち)。
2. **セーフポイントの条件を変える**。いま書き出すのは「ルートのコンテキストで、C の境目なし」のとき
   だけ。Fiber の中で止めるには、ルート → resume した Fiber → … のチェーンを全部書き、いちばん
   内側から続ける。Fiber は VM から resume されたものなら C のスタックを使わない
   (`vmexec` が偽) ので、原理的には運べる。C の関数から resume されたもの (`fiber2.rb` の
   `resume_by_c_func`) は C のフレームなので断る。

Task (mruby-task) もコンテキストは Fiber と同じ形 (各 Task がコンテキストを持つ) で、加えてスケジューラの
キュー (レディ・待ち・休止)・tick・`Task::Queue` を運ぶ。時刻に依る (tick) ので、往復で結果が
変わってよい部分が出る。

案: 段 P4 として「コンテキストの表」を形式に足し (v1 にするならここ)、まず VM から resume された
Fiber、次に Task。読む側の SabiRuby もコンテキスト (`Vm::contexts`) を持つので写せる見込み。

## 見立てと違った点

- **基準のオブジェクトは死ぬ**。P1 の形は「VM を開いた直後のものはずっとある」を前提に
  アドレスで名前を引いていた。`remove_const` で最後の参照が消えると回収され、空いた場所に
  別のものができる (#10)。1 回の往復では出ず、2 回目の書き出しで初めて出た。
- **復元で利用者のコードが走る**。P1 で「キーの hash は復元側で計算し直す」にしたので、
  入れ直しで `hash` / `eql?` が走る。副作用のあるキー (試験の callback) で初めて問題になった
  (#8・#9)。走る時点で、スタックも含めて状態がそろっている必要がある。
- **P1 の不具合の多くは、近道に隠れていた**: attr_writer の引数の仕様は、Object の
  attr_writer が VM の近道を通るので見えなかった (#3)。別名の Proc は「断る」と言いながら
  書き続けていた (#2)。
- **死んだレジスタは C の側でも効いた**。SabiRuby のためと見ていたが、試験一式では Fiber・
  IO を古いレジスタが指していて断る点が 3.7% あった。
- **乱数は 32bit と 64bit で違う**。mruby-random の PCG の乗数がポインタ幅で違う
  (`random.c`)。状態を運んでも、64bit から 32bit へ移ると続きの乱数が変わる。試験一式は
  乱数の値を比べないので食い違いにはならなかったが、同じシードから同じ列を期待する
  プログラムは、幅をまたぐと違う列を見る (mruby の側の差)。
- 試験一式は 102 ファイル全部で 2 秒ほどで流れる。点を 20 倍にしても数分。

## 撤回した仮説

- 「Time を運ばないなら assert.rb の `$test_start` を外せばよい」→ 方針どおり Time を運ぶ

- 「Hash の入れ直しを最後にすれば足りる」→ 入れ直しで走るコードは状態の全部を見うるので、

- C の関数が呼んだブロックの中 (5,426 点) は、C のスタックなので運べない。`sort { }` などを
  Ruby で書き直せば運べる点が増える (mruby の側の変更)。
- プロセスの資源 (ファイル・ソケット) は計画の範囲外。作り直す層 (開き直す手順を持つ) を
  後の段で考える。
- キーの `hash` の値を運べば入れ直しで利用者のコードを呼ばずに済むが、mruby の Hash が値を
  持っていない。
- `checkpoint_bundled.c` は gem の内部の構造体を写している。mruby を上げるたびに確かめる。
- SabiRuby: 種類 16〜24 と変更表の 8・9 (Hash の中身の 10) は「まだ運ばない」と断る。

## 決めてほしいこと

1. Fiber・Task を運ぶ段 (P4) を立てるか。立てるなら、形式にコンテキストの表を足すときに版を v1 に
   上げるか。
2. 基準のオブジェクトを全部持ち続けること (#10 の直し)。プログラムが手放した組み込みの
   オブジェクトも回収されない。増えるメモリは、基準のオブジェクトの数だけの値を持つ Array 1 つ。
3. 復元でキーの `hash` / `eql?` が走ること (Marshal.load と同じ)。副作用で Hash が変われば
   断る、でよいか。
4. 付属の gem の C のデータの項目 (`checkpoint_bundled.c`。gem の構造体の写し) を
   mruby-checkpoint に置いてよいか。各 gem の側に置くのが筋だが、vendor は触らない約束。
5. `END0` を必須にしたこと (P2 までのイメージは読めない)。
6. 形式の版を v0 のままにしたこと (種類 10 個・変更 3 個・セクション 3 個を足した)。
