# P1 報告: 形式 v0、同じプロセスの往復、64bit ⇔ 32bit

> この段の後で mruby-checkpoint に改名した (`Ghost.hop` → `Checkpoint.suspend` ほか、`doc/report/p1b.md`)。以下は当時の名前のまま。

> 状態: 実装済・検収待ち | 更新: 2026-11-02 | 指示は `doc/instruction_p1.md`

## 結果

- カウンタのプログラムが `Ghost.hop` の次の行から、別のプロセスで数え続ける。
  64→64、64→32、32→64、32→32 と、同じプロセスの新しい `mrb_state` の 5 通りで確認。
  2 回 hop するものは 64→32→64 のように行き来する。
- `rake test` は 11 本のサンプル × 組み合わせで 95 項目すべて通る。AddressSanitizer
  の版と、確保のたびに全 GC を走らせる版 (`MRB_GC_STRESS`) でも全サンプルの往復が
  一致する。
- 64bit 版と 32bit 版の mruby が書くイメージ (ghost の書き出したファイル) は、書いた側の
  ポインタ幅を記す 1 バイト以外同一。
- 対応しない型を持つ状態は、どのオブジェクトの何の型か、どこから届いたかを添えて
  `Ghost::Error` で断る。プログラムはそのまま続く。
- ベンチマークの普段の速さの差は、合計で −3.3% (patch のみ)、−3.7% (patch + gem)。
  ただし個別には −7.7%〜+10.8% と揺れ、その大半は命令列の配置の違いによるもので、
  この機械では「1% 以内」を個別の計測で示せない (§ベンチマーク)。判断を仰ぎたい。

## 選んだ方式と理由

### hop の止め方: フラグを立てて、次のセーフポイントで止まる

`Ghost.hop(path)` は C の関数で、呼ばれた時点では止まらない。やるのは 3 つだけ:
この `mrb_state` に「hop の要求あり」と行き先を記す、`mrb->task.switching` を立てる、
nil を返す。

`task.switching` は、VM が命令の境目ごとに既に見ている、タスク切り替えの要求のフラグ。
patch はその判定の遅い側 (フラグが立っているときだけ通る側) に、hook の呼び出しを足した。
hook が呼ばれる条件は、タスクを切り替えてよい条件と同じ: 例外が飛んでいる途中で
ない、ObjectSpace をなめている途中でない、ルートのフレームからいまのフレームまでの間に C の
関数を挟んでいない (`task_across_c_boundary()`)。

- 普通の呼び出しなら、`Ghost.hop` の呼び出し命令が終わった直後の境目がそれに当たる。
  戻り値 nil はもうレジスタに入っていて、pc は次の命令を指す。イメージにはその状態が
  そのまま入るので、復元側は特別な扱いなしに次の命令から始めればよい。
  「hop の次の行から」はこれで満たす。
- C の関数が呼んだブロックの中 (`sort { }`、`Array.new(3) { }`) では、その関数から
  抜けるまで要求が待たされ、抜けた直後の境目で止まる (`c_boundary.rb` で、最初の
  プロセスがすべての比較を出し終えてから hop することを確かめた)。拒否ではなく
  先送りにしたのは、C のスタックのフレームは運べないが、待てば必ず運べる点に来るから。
  Ruby で書かれた反復 (`Array#each`、`Integer#times`、`each_with_index`) は C の境目に
  ならず、ブロックの中でそのまま止まる。
- 書き出せない状態だったときは、hook が `Ghost::Error` を上げる。上がる場所は次の
  命令の境目なので、`begin ... Ghost.hop ... rescue Ghost::Error` で受けられる。

比べた案: 「hop のフレームを特別に扱い、C の関数の中で書き出して、戻り値を
復元側で入れる」は patch なしで済むが、C の境目の中での先送りができず、P3 の
「ランダムなセーフポイント」(C の関数を呼ばずに外から止める) にもつながらない。セーフポイントに
相乗りする形なら、止める理由が `Ghost.hop` でも外からの要求でも同じ API で済む。

### permanent の引き当て: 開いた直後の状態に名前を付ける

書く側はプログラムを読む前に、読む側は復元の前に、`mrb_ghost_baseline()` で同じ
手順を踏む:

1. VM を開いた直後の状態を決まった順 (シンボル名の順) になめ、届いたものに名前を
   付ける。クラスはそのクラス自身の名前 (`Integer`、`Math::DomainError`)、特異クラスは
   `S:`、mrblib の Ruby のメソッドの Proc は `M:Integer#times`、メソッド表の C の関数は
   `F:Array#length` など (`doc/format_v0.md` §8)。
2. クラスごとにメソッド表と ivar (定数・クラス変数を含む) とスーパークラス、main の ivar、グローバル
   変数、permanent な String / Array / Hash の中身のハッシュを控える。
3. 全 GC の後、ヒープに生きているオブジェクトを全部控える (名前の有無によらず)。
4. permanent な Proc の irep とその子孫の irep の内容のハッシュを控える。

書き出しでは、名前のあるものは名前だけを書く。控えにあるのに名前の無いものに
届いたら断る。permanent への変更は 2 の控えとの差分として書く (メソッドの追加・
置き換え・削除、ivar・定数の設定・削除、スーパークラスの付け替え、グローバル変数)。プログラムが
作ったトップレベルのクラスは「Object への定数の設定」として、トップレベルの `def`
は「Object への private なメソッドの定義」として現れる。差分の無い permanent な
ものはイメージに出てこない。カウンタのイメージは 375 バイト、いちばん大きい `user_class.rb` で
3 KB ほど。

名前で結ぶので、シンボル ID・ポインタ・ROM に置かれたメソッド表の違いは効かない。
同じビルドなら名前は必ず一致する。

### Env: スタック上のものは「スタックの位置」で書く

ブロックやクロージャが捕まえたローカル変数の箱 (Env) は 2 通りある。

- フレームがまだ動いているもの: フレームのレジスタそのものを指していて、フレームとクロージャが同じ
  変数を共有する。書き出しでは中身を写さず、スタック配列の位置だけを書く
  (その位置がフレームの R0 と一致し、そのフレームが Env を指していることを確かめる)。復元では
  組み立てたスタックのその位置を指させる。
- フレームが終わったもの (切り離し済み): 値を自分で持つので、そのまま書く。

書き出す前に Env を切り離す案は採らなかった。切り離すとフレームのレジスタとクロージャの
変数が別物になり、実行中のフレームが書いた値がクロージャから見えなくなる。
`closure.rb` は両方の場合を、hop の後に外の変数を書き換えて確かめる。

### irep: 内容のハッシュで識別し、プログラムのものは中身を運ぶ

irep の ID は内容 (ローカル変数とレジスタの数、命令列と例外処理の表、プール、シンボル
名、子のハッシュ) の FNV-1a 64 bit。ポインタ幅に依らない。permanent な irep はハッシュ
だけ書き、読む側は控えから同じハッシュのものを引く (mrblib の `Integer#times` の中で
止まったフレームなどがこれを使う)。プログラムの irep は中身を運び、読む側で組み立てて
からハッシュを計算し直して照合する。

### GC

書き出しの間は GC を止める (書き出しはヒープをほとんど触らない)。書き出し前の
全 GC は要らなかった: ルート (VM のスタックとフレーム、permanent への変更) からたどれるもの
だけを書くので、ゴミは自然に落ちる。復元は GC を止めたまま全部を組み立て、ルートに
つないでから全 GC を 1 回走らせる。書き込みの障壁を個々に呼ばなくても、全 GC が
ルートから全部を塗り直す。

## 当てた patch

`patches/0001-vm-safepoint-hook.patch` (`src/vm.c` のみ、+48 −4 行):

- `void (*mrb_vm_safepoint_hook)(mrb_state*)` を足す (既定は NULL)。
- `RETURN_IF_TASK_STOPPED` (命令の境目ごとに展開される判定) を、`task.switching` と
  コンテキストの終了のフラグの 2 つを読んで分岐するだけにし、遅い側を 1 か所の
  `L_TASK_CHECK` と関数 `task_stop_requested()` にまとめた。その関数が、タスクを
  切り替えてよい条件のときに hook を呼び、元と同じ条件でスケジューラへ戻るかを
  決める。元の判定の意味 (ルートのコンテキストでは切り替えない、例外の途中・C の境目では
  先送り、終了は先送りしない) は変えていない。
- switch で命令を振り分ける構成 (`MRB_USE_VM_SWITCH_DISPATCH`) では、判定は各所で
  `task_stop_requested()` を呼ぶ形のまま。

`mrb_data_type` にはフィールドを足していない。C のデータは gem の中の別表 (型へのポインタ →
名前と dump / restore の関数) で扱い、`Ghost::Box` を 1 つ登録して試験した。

## 試験の結果

`rake test`: 95 項目すべて通過。各サンプルについて、往復なしの出力 (64bit) が
`test/samples/*.out` と、32bit の往復なしの出力と一致し、同じプロセスの新しい
`mrb_state` (64・32) と 64→64・64→32・32→64・32→32 の hop をつないだ出力が往復なしと
完全に一致する。`hop-after` のマーカーのあるサンプルは、最初のプロセスの最後の行で
止まった位置も確かめる。途中で書かれたイメージはすべて、仕様書だけを見て書いた
`tools/ghost_inspect.rb` でも最後まで読めることを確かめる。

| サンプル | 確かめること | イメージ |
|---|---|---|
| counter | hop の次の行から数え続ける、2 回 hop | 375 B |
| method_middle | メソッド 3 段の途中、位置引数・省略可能引数・残り引数・キーワード引数 | 1.2 KB |

`refuse.rb` の出す理由の例:

```
refused: C data of class Time (type 'Time') has no entry in the ghost data table (stack slot 1)
```

復元にかかる時間は、どのサンプルでも `time` の分解能 (10 ms) 未満。

## ベンチマークの差

`rake bench`: 64bit、同じ設定の 3 つのビルド (patch なし / patch のみ / patch + gem)
を 1 つの CPU に固定して交互に 9 回ずつ走らせた中央値 (秒)。

| ベンチマーク | patch なし | patch のみ | patch + gem | patch のみの差 | gem ありの差 |
|---|---|---|---|---|---|
| bm_fib | 2.287 | 2.111 | 2.118 | −7.71% | −7.38% |
| bm_so_lists | 0.335 | 0.329 | 0.331 | −1.63% | −1.25% |
| bm_ao_render | 3.043 | 2.955 | 2.926 | −2.92% | −3.86% |
| bm_so_mandelbrot | 0.614 | 0.680 | 0.675 | +10.76% | +9.94% |
| bm_mandel_term | 0.011 | 0.011 | 0.011 | (短すぎて測れない) | |
| 合計 | 6.290 | 6.085 | 6.060 | −3.26% | −3.65% |

(`bm_app_lc_fizzbuzz` はこの版の構文解析器で構文エラーになるので外した。)

gem の有無の差 (patch のみ ⇔ patch + gem) は 1% 以内。hook が登録されていても、フラグが
立たない限り通らないので、これは期待どおり。

patch の有無の差は個別に大きく揺れる。調べたこと:

- patch の形を 3 通り試した。(1) 元の判定の中に hook の呼び出しを足しただけ: `vm.o` の
  命令列が 81 KB → 97 KB に増え、mandelbrot +15%。(2) 遅い側を境目ごとに関数呼び出しに:
  77 KB、mandelbrot +13〜20%、fib −2%。(3) 遅い側を 1 か所にまとめた (採用): 72 KB、
  mandelbrot +7〜11%、fib −7%、ao_render −3〜−6%。
- 対照として、元の `vm.c` に**使われない関数を 1 つ足しただけ**の版を作ると、
  mandelbrot が +4% 遅くなった (fib・ao_render は ±0)。
- mandelbrot の時間の大半は `OP_MOVE` の処理の中の 1 命令 (16 バイトの値の格納) に
  かかっていて、その処理の機械語は patch の前後でほぼ同じ (読み込み 1 つの順序だけが
  違う)。

この 3 つから、mandelbrot の +10% は判定の仕事の量ではなく、巨大な `mrb_vm_exec` の
命令の配置が変わったことによるものと見ている。この機械 (WSL2) では命令数などの
ハードウェアの計数器が使えず、配置の影響を除いた比較ができない。「1% 以内」を
個別のベンチマークで示すには、計数器の使える機械か、本番の機体 (ESP32) で命令数か
サイクル数を比べるのがよいと思う。

## 見立てと違った点

- **ルートのコンテキストでは、タスク切り替えの判定は決して成り立たない**。`RETURN_IF_TASK_STOPPED`
  は、ルートのコンテキスト (タスクでないプログラムの本体) では切り替えを見送る (上流の
  #6887 の対策)。そのため「切り替えられる点 = 運べる点」をそのまま使うことはできず、
  hook は「ルートの規則を除いて切り替えてよい点」で呼び、スケジューラへ戻るかどうかの
  判断とは切り離した。相乗りの方針自体は守れている (同じフラグ・同じ条件・普段は通らない)。
- **判定の形を変えると、意味が同じでも速さが ±10% 動く** (§ベンチマーク)。最初の
  patch (判定の中に呼び出しを足すだけ) は意味も手間も最小だったが、mandelbrot が
  15% 遅くなった。
- mruby の標準の gembox は `mruby-bin-debugger` (mrdb) を含み、その gem が
  `MRB_USE_DEBUG_HOOK` を有効にする。命令の境目ごとに `code_fetch_hook` の確認も
  走っている。Family mruby の構成とは違うはず。
- Prism は mruby の中の submodule で、`vendor/mruby` からは取り出されていなかった。
- 作り込みの細部: 別名のメソッドの Proc (`MRB_PROC_ALIAS`) は本体に irep でなく
  シンボルを持つ。子の数が 1 以上なのに子の表が NULL の irep がある (mrblib の中)。
  例外のバックトレースは圧縮された内部オブジェクトのことがあり、書き出しで
  String の Array に直す (書いた側の例外も Array に置き換わる)。`Fixnum` は `Integer`
  の別名の定数で、定数の名前順で名付けると `M:Fixnum#times` になってしまったので、
  クラス自身の名前を優先するようにした。

## 撤回した仮説

- 「書き出しの前にフル GC と Env の切り離しが要る」→ どちらも要らなかった
  (§GC、§Env)。
- 「遅い側を関数に追い出せば普段の速さは変わらない」→ 配置の影響のほうが大きい。
- 「ルートで止めるには、プログラムを Task として走らせ、既存の『スケジューラへ戻る』
  道を使うしかない」→ hook をルートの規則から切り離せば、ルートのまま止められた。
  Task を運ばずに済む。
- 「Hash は書き出しでキーごとに引き直して書く」→ 書き出しの途中で利用者の `hash`
  メソッドが走ってしまう。表をそのままなめて書き、キーのハッシュ値は復元側で計算し
  直す形にした。

## 残件 (P2: SabiRuby の側で要りそうなこと)

- **permanent の名前の対応表**。SabiRuby の組み込みのクラス・メソッド・C の関数
  (`F:Array#length` など) に、mruby 側と同じ名前を付ける手順が要る。形式 v0 は
  「同じビルドなら同じ名前」で作ってあり、処理系をまたぐ一致はまだ保証していない。
- **mrblib の irep のハッシュが合わない見込み**。SabiRuby は mrblib を mruby
  4.1.0-rc2 の mrbc で作って埋め込んでいるので、この mruby (`f56d44ecc`) の mrblib と
  中身が違えば、mrblib のメソッドの中で止まったフレーム (`times`・`each` のブロックの中で
  hop した場合) を結べない。案: permanent な irep の中身も運べるようにして相手側で
  使う、mrblib の中のフレームを含む状態は断る、mrblib の版をそろえる。
- フレームの写し方: フレームの R0 = 呼んだ側の R[a] というレジスタの窓、pc の意味
  (いちばん上は次の命令、下は戻り先)、引数の数 (15 = 詰めた)、可視性のフラグ、渡された
  ブロック、環境。SabiRuby は同じ配置の設計なので写せるはずだが、フレームの構造体の
  対応を決める必要がある。
- スタック上の Env を「スタックの位置」で共有させる仕組み。
- 例外処理の表、命令の集合は RITE 04.00 で共通のはず。確かめる。
- 行番号 (デバッグ情報) は v0 で運んでいない。SabiRuby の `Vm::next_line` などと
  合わせるなら運ぶ。
- 多倍長整数のプールは mruby の内部の詰め方のまま (不透明)。

## 決めてほしいこと

1. **速さの受け入れ条件の測り方**。この機械では個別のベンチマークが配置の影響で
   ±10% 動き、「1% 以内」を wall clock で示せない。合計 (−3.3%) で可とするか、
   計数器の使える機械・ESP32 での命令数で測り直すか。
2. 先送りの扱い。C の境目の中の hop は「抜けた直後に止まる」にした。抜けないまま
   プログラムが終わると hop は起きない (いまは何も言わない)。断る・警告するの
   どちらかにするか。
3. P2 の mrblib の irep のハッシュの扱い (上の 3 案)。

## mandelbrot の遅れの原因 (追加の調査)

§ベンチマークの差で「配置の影響と見ている」とした bm_so_mandelbrot の +7〜11% を、
測って確かめた。同じ 64bit・同じ設定のビルドを使い、`vm.c` だけを作り直して
`libmruby.a` の `vm.o` を差し替える形で変種を作った (手で作り直した patch なし・
patch のみのビルドは `rake bench` のものと命令列が一致することを確かめてある)。
時間は 1 つの CPU に固定し、交互に 7〜9 回走らせた中央値。命令数は valgrind
(cachegrind・callgrind、コンテナの中) で数えた。この機械は WSL2 の上の
13 世代 Core (Raptor Lake) で、ハードウェアの計数器は使えない。

### 命令数: patch のほうが少ない

| ベンチマーク | patch なし | patch のみ | 差 | 時間の差 |
|---|---|---|---|---|
| bm_so_mandelbrot | 13,514,353,920 | 12,885,439,842 | −4.65% | +10.2% |
| bm_fib | 46,713,897,627 | 45,932,132,192 | −1.67% | −7.1% |
| bm_ao_render | 56,795,979,384 | 56,069,269,481 | −1.28% | −3% 前後 |

mandelbrot の命令はほぼすべて `mrb_vm_exec` の中 (98%)。減った分は、命令の境目の
判定が `mrb` をスタックから読み直さなくなったこと (`OP_MOVE` の NEXT で 1 回あたり
2 命令、3.10G → 2.76G) と、`OP_MUL` などで `regs` をスタックに退避しなくなった
こと (`OP_MUL` 2.44G → 2.33G)。patch は mandelbrot でも仕事を減らしている。
命令数が 4.7% 減って時間が 10% 増えたので、1 命令あたりの時間が約 15% 延びている。

### 打ち消したもの

- **関数の位置 (全体のずらし)**。`libmruby.a` の前に 16〜2048 バイトの詰め物を
  置いて全体をずらした。patch なしは 0〜+6.8% (9 通り中 6 通りは ±1% 以内)、patch のみはどの
  ずらしでも +9.7〜+10.7% で、patch のみが速くなる位置はなかった。ただし全体の
  ずらしは命令どうしの相対位置を変えないので、これだけでは中の配置の影響を
  否定できない (下で中の配置を動かした)。
- **揃えの指定・並べ方の指定**。

  | 指定 | patch なし | patch のみ |
  |---|---|---|
  | (なし) | ±0 | +7.5% |
  | 揃えをすべて 1 | −0.7% | +7.0% |
  | `-falign-jumps=32` | −2.4% | +6.3% |
  | `-falign-jumps=64` | −2.8% | +4.7% |
  | `-falign-labels=32` | −1.6% | +9.2% |
  | `-falign-functions=64` | −1.0% | +7.7% |
  | `-freorder-blocks-algorithm=simple` | −1.5% | +4.8% |
  | `-fno-crossjumping` | +0.2% | +24.5% |
  | `-fno-tree-tail-merge` | +1.0% | +9.2% |

  (差はどれも patch なしの既定のビルドに対して。)
- **命令の置き場所の広さ**。mandelbrot で 500 万回以上実行される命令が占める範囲は、
  patch なし 64 バイトの行 66・32 バイトの窓 99・4KB のページ 15、patch のみ 55・
  88・12。分岐して飛ぶ回数は 1,269M → 932M。patch のほうが狭く、飛ぶ回数も
  少ない。valgrind の模擬 (この CPU と同じ 32KB・8 way・64 バイト行の命令
  キャッシュ) では命令キャッシュの外れが 0.31M → 2.42M と増えるが、1 回 20 サイクル
  としても 1% に届かず、後述の詰め物の変種では外れの数と時間が対応しなかった
  (外れ 1.72M の変種が +30%、2.89M の変種が +3%)。模擬の分岐予測の外れも
  191.0M と 192.8M でほぼ同じ。
- **判定の形**。patch の判定の書き方を変えても、patch なしの速さには戻らない。

  | 変種 | mandelbrot |
  |---|---|
  | patch のみ (採用の形) | +9.3% |
  | `mrb_unlikely` を外す | +6.1% |
  | `mrb_unlikely` を 2 つの条件に別々に | +9.7% |
  | 共有の飛び先をやめ、境目ごとに関数を呼ぶ | +13.2% |
  | patch なしの条件のまま、遅い側だけ共有の飛び先へ | +2.4% |

### 中の配置を動かすと、patch のみだけが大きく揺れる

実行されない詰め物を、冷えた命令 (`OP_STOP`・`OP_DEBUG`・`OP_KARG`) の処理の中に
`jmp` で飛び越す形で入れ、大きさを 0〜63 バイトで乱数にして 12 通り作った。
処理の並び順は変わらず、命令数はビルドごとに一定 (patch なし 13,514.4M、
patch のみ 12,885.5M、どの詰め物でも ±0.01M) のまま。

| | 12 通りの範囲 (patch なしの既定に対して) |
|---|---|
| patch なし | −2.8% 〜 +0.4% |
| patch のみ | +3.2% 〜 +32.2% (うち 2 通りが +29.6%・+32.2%) |

GCC は patch のありなしで処理の並び順をまるごと変えている (たとえば `OP_MOVE` の
入口は関数の先頭から patch なし +0x4659、patch のみ +0x3108)。すべての境目が
1 つの共有の飛び先へ枝を持つようになり、流れの形が変わったため。そこで
`-freorder-blocks-algorithm=simple` で両方の並び順をソースの順にそろえ、同じ
12 通りの詰め物で測った。

| 並び順をそろえて | 12 通りの範囲 |
|---|---|
| patch なし | −2.7% 〜 +0.7% |
| patch のみ | +2.6% 〜 +4.6% |

並び順をそろえると +30% の崖は消えるが、約 5% の差がどの配置でも残る。

### 残る 5% は patch の仕事ではなく、`OP_MOVE` の写し方との組み合わせ

- 小さな試験で分けると、整数だけの繰り返しでは patch のほうが速く (空の `while`
  −13.3%、整数の掛け算と足し算 −5.2%、`MOVE` だけ −7.4%)、Float の計算を
  続けて写す繰り返しで遅い (+1〜+6%)。
- mandelbrot のバイトコードは、`MUL`・`ADD` の結果をすぐ `MOVE` で別のレジスタへ
  写し、写した先を次の `MUL` が読む形が続く。Float の結果は `movl` (型 4 バイト) と
  `movsd` (値 8 バイト) の 2 回に分けて書かれ、`OP_MOVE` はそれを 16 バイト 1 回で
  読む (`movdqu`)。書いた直後の小さい書き込み 2 つを大きい 1 回で読むので、
  書き込みの値をそのまま渡す近道 (store forwarding) が効かず、書き込みが
  メモリに届くまで待つ。この待ちは両方のビルドにある。前の報告の「`OP_MOVE` の
  16 バイトの格納 1 命令に時間がかかる」は、この読み込みの待ちが次の命令に
  付いて見えていたもので、時間の標本の数は patch なし 7,086・patch のみ 7,166 と
  同じ。差はそこにはない。
- `OP_MOVE` の写しを「値 8 バイトと型 4 バイトを別々に」に変えると (意味は同じ。
  余白の 4 バイトを写さないだけ)、差が逆転する。並び順をそろえ、詰め物 8 通りで:

  | `OP_MOVE` を分けて写す | 8 通りの範囲 |
  |---|---|
  | patch なし | +15.2% 〜 +17.7% |
  | patch のみ | +0.1% 〜 +3.4% |

  同じ書き換えで patch なしは 16% 遅くなり、patch のみは patch なしの元の速さに
  戻る。速いか遅いかを決めているのは、判定の手間ではなく、`regs` の配列を介した
  「書いた直後に読む」の連なりを CPU がどう処理するかである。
- 時間の標本 (perf の cpu-clock、6 回分) で比べると、patch のみで増えた時間は
  特定の命令の処理に集まらず広く散り、処理の入口 (前の処理からの間接分岐の
  直後) が全体の 7.9% → 9.2% に増える。+30% の崖の配置では、増えた時間が
  `MUL`・`ADD` の入口で「直前の `MOVE` が書いたばかりのレジスタの型を読む」
  読み込みに集まる (100 万標本あたり `MUL` 14,697 → 32,361、`ADD` 2,598 → 14,602)。
  命令列はまったく同じで、違うのは番地だけ。

### 結論

mandelbrot の遅れは、patch が仕事を足したためではない。patch のみの命令数は
3 つのベンチマークすべてで少ない (mandelbrot −4.65%)。また、関数の位置・揃え・
命令の置き場所の広さといった命令取り込みの側の配置でもない。

原因は、`regs` の配列を介して「書いた直後に読む」命令の連なり (Float の結果を
2 回に分けて書き、`OP_MOVE` が 16 バイトで読み、次の処理がその型を読む) の
処理に、この CPU がどれだけ時間をかけるかである。これが命令の番地と周りの
命令の並びで大きく変わる。番地だけを変えると 0〜+30% 動き、`OP_MOVE` の写し方を
変えると patch のありなしの順位が入れ替わる。patch は判定の流れの形を変えるので、
GCC が処理の並び順とレジスタの割り当てをまるごと変える。その結果が mandelbrot
では悪い側に、整数の処理では良い側に出た。

CPU の中のどの仕組みか (読み込みを書き込みより先に実行してよいかの予測が外れて
やり直しになっているのか、書き込みが届くのを待つ長さが変わっているのか) は、
計数器が使えないので区別できていない。標本が「直前に書いたレジスタの型の
読み込み」に集まること、命令の番地だけで崖が出ることから、命令の番地で引く
予測の表 (読み書きの依存の予測) が当たっていると見るのがいちばん合う。
1 つの CPU の上の、x86 の投機実行に固有の効果である。

前の報告の 3 つの根拠のうち、(a) 使われない関数を足すと +4% は、この配置への
敏感さと合う。(c) は上で直した (待っているのは読み込みで、差はそこにない)。

### 直し方の案 (採用はしていない)

- patch の中の書き方 (`mrb_unlikely` の付け方、遅い側を関数にするか共有の飛び先に
  するか、遅い側を置く場所) では、どれも +2〜+13% に収まり、安定して元に戻る形は
  なかった。
- `OP_MOVE` を値と型に分けて写すと、patch のみのビルドは 4 つとも patch なしより
  速くなる (mandelbrot −1.1%、fib −3.7%、ao_render −5.7%、so_lists −3.1%)。ただし
  safe point の patch の外の mruby 本体の書き換えで、同じ書き換えが patch なしでは
  mandelbrot を 20% 遅くする。この CPU の都合を追いかけるだけなので勧めない。
- 速さの受け入れは、ホストでは命令数 (valgrind) で見て、時間は本番の機体 (ESP32、
  命令を順に実行する核で、この種の投機はない見込み) で測るのがよいと思う。
  ホストで時間を比べるなら、1 つのビルドどうしでなく、冷えた処理に詰め物を入れた
  変種を十数通り作って範囲どうしを比べる。
