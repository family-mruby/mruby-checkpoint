# 報告: 基準を作る間の量を減らす (F6、S3 のため)

> 状態: 実装済・検収待ち | 更新: 2026-11-06 | Family mruby の S3 (アプリのプール 500 KB) に gem を入れるため、VM を開くときに基準を作る間だけ要る量を減らした。固定の表を使う 32 bit のドライバ (既定の gembox、1,719 名前) で、作る間の一時的な量は 65,995 → 9,830 B (−85%)、作った後に残る量 (割り当てから見た量) は 45,836 → 20,429 B (−55%)。名前・書き出す表・イメージは前と同じ

Family mruby の側の数字 (S3 の gem の組み合わせ、端末ごとの前後) は fmruby-core の `doc/checkpoint/report/f6_s3.md`。

## 1. 何が多かったか

基準は VM を開いた直後に、そのプールの中で作る。作る間は、名前を付けたものを引くための表を持つ。固定の表 (Ff) を
使っても、その表は VM をなめて作っていたので減っていなかった (Ff の報告の 1.2)。32 bit で名前 N 個のとき:

| もの | 前 | 中身 |
|---|---|---|
| ポインタ → 名前の番号 (オブジェクト用と C の関数用の 2 つ) | 1 枠 8 B、半分まで埋める 2 の冪の大きさ、伸ばすときに古い表と新しい表が両方ある | 名前ごとに 1 つ |
| irep → 番号 | 同じ | mrblib の irep ごと |
| irep の一覧 | 16 B (ポインタとハッシュ、32 bit では詰め物が 4 B) × 2 の冪 | 表と同じなら最後はポインタだけ残す |
| 表の名前 → snapshot | 4 B × 表の名前の数 | |
| 名前で中身をたどる待ち行列 | 名前の写し (文字列) + 8 B | 中身に名前を付けるものごと |
| 要素としてだけ持たれる String の集合 | 1 枠 8 B、半分まで | |
| 並べ替えの番号 | (アドレス, 番号) の組 8 B を qsort | 作り終わるとき |
| クラスの名前 | `mrb_class_path` が毎回新しい String を作る (ごみ) | 訪ねたクラスごと |

最後のものはプールの中でごみのオブジェクトになり、オブジェクトのヒープのページを 1 枚増やしていた (作った後にも
残る量に数えられていた。32 bit で約 20 KB)。

## 2. 減らした工夫

1. **ハッシュ表は番号だけを持つ**。枠には名前 (irep) の番号 + 1 だけを入れ、ポインタは名前の表 (`ptrs`、どのみち
   残すもの) から引く。番号が 65,535 以下なら 16 bit の枠。オブジェクトと C の関数を 1 つの表にした (引くときに
   「C の関数か」も照らす)。3/4 まで埋め、大きさは 2 の冪に限らない。固定の表があれば、表の名前の数・irep の数で
   最初から大きさを決める (伸ばし直しが無い)。
2. **irep はポインタだけ持つ**。表があれば、見つけた順にハッシュを表のものと比べ、違いがあったことだけを覚える。
   違ったときは作り終わりに、各 irep を「表の同じハッシュの項の番号 (16 bit)」で結び、表に無いものだけハッシュを
   持つ (`irep_tix`・`irep_own`)。前は違うと全部の irep を 16 B で持った (Family mruby の P4 の実機は表と irep が
   違い、27,600 B 持っていた。同じ形なら 1,725 × 6 B ほど)。表が無いときはポインタとハッシュを別の配列で持つ (12 B)。
3. **待ち行列は名前の番号**。名前の文字列は表 (または状態の名前の塊) から引き、たどる間だけ 1 つの作業の
   バッファに写す (状態の名前の塊は伸びると動くので)。
4. **表の snapshot は名前で探す**。表は snapshot を名前の順に書く (作るときの順がそうなる) ので、二分探索で足りる。
   順になっていない表 (無いはずだが) のときだけ前の表を作る。
5. **表と違って見える snapshot は (番号, 場所) の組の並び**。前は表の snapshot の数ぶんの配列 (P4 で 3,460 B)。
6. **並べ替えはその場で**。残す 3 つの索引 (`obj_idx`・`func_idx`・`irep_idx`) は 16 bit の項 (名前と irep の数が
   65,535 以下のとき) にし、ヒープソート (同じキーは番号の順) でその場で並べる。名前の順の並べ替え (メソッド・
   ivar・グローバル変数) もヒープソートにした (並べる名前は互いに違うので安定でなくてよい)。
7. **クラスの名前は String を作らずに読む**。クラスが名前 (`__classname__`) を持っていればそれを写す。持たない
   ときだけ `mrb_class_path` を呼び、アリーナを戻す。
8. 表があるとき、集めたメソッドとクラスの ivar はその場で並べる (写しを作らない)。メソッドは先に数えて配列を
   1 回で取る。基準のときのオブジェクトの配列も先に数えて 1 回で取る。

入れなかったもの:

- **C の関数の番地を表に入れる** (Ff の 2 章の (a))。VM ごとの `ptrs` のうち C の関数の分と `func_idx` が要らなく
  なる (32 bit で関数ごとに 6 B。Family mruby の S3 で約 1,000 個、約 6 KB)。mruby・picoruby の C のメソッドの
  大半は `static` で、各 gem のソースに手を入れる (static を外すか登録の表を足す) 必要がある。減る量に比べて手が
  大きいので見送った。
- **作る間の表を埋め込む側のアロケータから取る** (dump・restore の作業の領域と同じ `mrb_checkpoint_set_allocator`)。
  プールから一時的な量を無くせるが、上の工夫で一時的な量は小さくなったので見送った (Family mruby の報告の選択肢に
  書いた)。

## 3. 数字

ドライバ (`tools/checkpoint`) に、状態の割り当てを数える計り (`CHECKPOINT_BASELINE_SIZE`) を足した。割り当てごとに
頼まれた大きさを数え、基準を作る前後の使用量と最高位を出す (`baseline took N bytes of the allocator (M more while it
was made)`)。プールの頭の分は含まない。

既定の gembox、試料の前置き込み (1,719 名前):

| ドライバ | 部分の合計 前 → 後 | 残る量 前 → 後 | 作る間の一時的な量 前 → 後 |
|---|---:|---:|---:|
| 表あり 32 bit | 26,069 → 21,487 | 45,836 → 20,429 | 65,995 → 9,830 |
| 表あり 64 bit | 39,157 → 34,587 | 79,123 → 33,161 | 96,887 → 15,026 |
| 表なし 32 bit | 108,790 → 104,206 | 128,537 → 103,128 | 77,469 → 44,234 |
| 表なし 64 bit | 127,670 → 123,098 | 167,596 → 121,632 | 112,993 → 54,710 |

- 部分の合計の差は、索引が 16 bit になった分 (表ありで 4.6 KB)。
- 残る量の差の大半は、クラスの名前のごみ (ヒープのページ) が無くなった分。
- Family mruby の S3 の gem の組み合わせ (3,403 名前、ホストの 64 bit) では、残る量 104,232 → 82,472 B、作る間の
  一時的な量 271,744 → 23,272 B (fmruby-core `doc/checkpoint/report/f6_s3.md`)。

## 4. 変わらないこと

- 名前の一覧 (`checkpoint names`)・書き出す表 (`checkpoint table`) は前の gem とバイト単位で同じ (表なしの 64 bit で
  確認した)。名前の決まりの版 (`MRB_CHECKPOINT_TABLE_VERSION`) と形式の版は変えていない。
- 引く順の結果: 同じポインタに 2 つの名前がある場合の引き当ては、前は qsort の順 (決まらない) で、今は番号の小さい
  方。ハッシュ表に同じキーを入れ直すと上書きする (前と同じ)。
