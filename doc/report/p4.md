# P4 報告: Task と Fiber、形式 v1、Family mruby と同じ起動の形

> 状態: 実装済・検収待ち | 更新: 2026-11-03 | 指示は `doc/instruction_p4.md`

## 結果

- 形式を v1 にした (`doc/format_v1.md`)。VM の部分が、実行のコンテキストの表 (root・Task ごと・Fiber
  ごとのスタックとフレームと状態)、今のコンテキスト、スケジューラ (Task をキューの順に、時計、待ちの
  残りの tick) になった。Task と Fiber はオブジェクトの種類 26・27、Task::Queue は C のデータの
  別表の項目として運ぶ。行番号のセクション `DBG0` ほか P3 の追補はそのまま正式のセクションにした。
- Fiber の中・Task の中・Task が待っている最中・Task の中の Fiber の中で、書き出して続けられる。
  断るのは C の関数のフレーム (C のスタックにあるもの) だけになった。
- `checkpoint run --as-task` (プログラムの本体を Task にして `mrb_task_run`。Family mruby の
  アプリの起動の形) を足した。サンプルの試験と試験一式の外からの停止は、両方の形で流す。
- 試験のビルド (`build/fuzz`) の mruby-task を仮想の時計にした (`mrbgems/hal-task-virtual`)。
  tick はスケジューラが空いたときと root が sleep したときに進み、`--quantum N` で N 命令ごとにも
  進む。普段のビルドは今の POSIX のタイマのまま。
- 長い版 (シード 1〜20、1 ファイル約 200 点、P3 と同じ規模) で、往復なしと食い違った実行は、除外の
  表の正当な違いを除いて **0** (top-level の形・Task の形とも)。P3 で断っていた Fiber・Task に
  関わる 5 つの理由 (P3 の長い版で 18,901 点) は **0** になった。残る Fiber・Task 関係の断りは、
  C の関数が yield した Fiber が待っている場合 (C のフレーム。原理的に運べない) だけ。
  (数字は §試験の数字)
- SabiRuby のリーダーを v1 に合わせ、Fiber と Task を組み立てて続けるようにした (片道)。
  サンプルのイメージは両方の形ですべて SabiRuby でも続き、出力が一致する。
- 復元の後に例外を起こすと、バックトレースの行番号が往復なしと一致する (`lines.rb`: root・
  Fiber・Task で、64 ⇔ 32、別のプロセス、Task の形、SabiRuby)。
- 普段のビルドの `vm.c` の patch は変えていない (valgrind の命令数の比較はしていない)。
- 調べる途中で、mruby-task・mruby-fiber 自身の不具合を 5 つ見つけた (§上流の不具合)。直して
  いない (止まる条件: mruby-task の作りや振る舞いを変えることになる)。試験の道具と除外の表で
  扱いを決めた。

## v1 で足したもの

`doc/format_v1.md` §16 に一覧。要点:

- **実行のコンテキストの表** (§10): コンテキストごとに状態 (未開始・実行中・resume して待機中・
  中断中・transfer して待機中・終了)、prev (resume したコンテキスト)、Fiber のオブジェクト、
  スタック、フレーム。root が 1 番、Task のコンテキストが続き、Fiber のコンテキストは届いた順。
- **フレームの種類**: Ruby のフレームに加えて「コンテキストの切り替えを待っている C の関数のフレーム」(`Fiber#resume`・
  `Fiber#transfer`・`Fiber.yield`・`Task.run`・`Task.pass`)。待っているコンテキストのいちばん上にだけ現れ、
  関数の名前を持つ。呼び出しの値は、切り替えで戻ってきた側がその窓の始まりに入れる。
- **スタック上の Env** はコンテキストの番号を持つ。
- **スケジューラ** (§11): 切り替えの要求、ループが回っていたか、1 tick のミリ秒、tick、次に起きる
  時刻の残り、Task (キューごとにキューの順。状態・キュー・優先度・待ちの理由と中身・名前・戻り値・時間の
  タイムスライスの残り)、実行中だった Task、埋め込む側の Task。
- **Task::Queue**: C のデータの別表の項目 (閉じているか)。中身は ivar `@items`、待っている Task は
  Task の表が Queue のオブジェクトを指す。
- **続け方** (§12): 読む側が何を始め直すかを、形式の一部として書いた。

## Task・Fiber の運び方

### 書く側

- セーフポイントの hook は、P1 からの patch のまま、Task のコンテキストの中でもスケジューラへ戻る前に呼ばれて
  いた (判定の `task_stop_requested` が hook を先に呼ぶ)。v1 では、どのコンテキストにいても書く。
- 書くのは、root、キューにいる全部の Task のコンテキスト、今のコンテキスト、そこから届くコンテキスト (Fiber のオブジェクト、
  prev、スタック上の Env のコンテキスト)。コンテキストとオブジェクトは互いに届くので、両方の待ち行列が空になる
  まで交互に書く。
- 全部のコンテキストの全部のフレームを見て、C から入ったフレーム (cci が 0 でない)・待っているコンテキストのいちばん上
  以外の C の関数のフレーム・表に無い C の関数で待っているコンテキスト・C から resume された Fiber (vmexec) を
  断る。Task のコンテキストの vmexec は、実行中の Task では立っているのが正しい (スケジューラの C のフレームは
  読む側が作り直す)。
- 実行中だった Task は、今のコンテキストから prev をたどって最初に当たる Task のコンテキストの持ち主 (無ければ
  ready のキューで RUNNING のもの)。自分を止めた Task は、その境目でもう DORMANT のことがある。
- スケジューラを入れた側 (実行中だった Task のコンテキストの prev) は、`Task.run`・`Task.pass` の C の
  関数のフレームか、フレームの無い root (埋め込む側が C から `mrb_task_run`) でなければ断る。
- 時刻は書いたときの tick と、各待ちの残りの tick (期限 − tick) で書く。

### スケジューラのフラグ

`task.switching` はスケジューラのフラグでもあり、しかも C の bool で、要求が立てた後にスケジューラも
立てたかを後から見分けられない (2 などの別の値を入れる案は、bool なので成り立たなかった)。そこで:

- 要求は、フラグがもう立っていればそのまま (スケジューラの要求がある)、立っていなければ立てて、
  そのときのスケジューラの様子 (実行中の Task、待ちキューと理由、レディキュー) を控える。
- セーフポイントでは、控えとの差で、スケジューラが間に切り替えを要求したかを決める: 実行中だった Task が
  もう RUNNING でない・中断された・タイムスライスが尽きた、待っていた Task が起きた (join の待ちは
  mruby-task と同じく優先度が上のときだけ)、優先度が上の Task がレディキューに入った。要求していれば
  フラグを残し (VM はすぐスケジューラへ戻る)、イメージには「その境目でタイムスライスが終わる」と書く。要求して
  いなければフラグを消して続ける。
- 見分けられないのは、外からの要求とセーフポイントの間の 1 命令が `Task.pass` だった場合だけ (フラグを立てる
  ほかに何もしない)。その pass は失われ、Task はタイムスライスが尽きるまで続く (止まることはない)。
  `Checkpoint.save` の呼び出しの中ではこれは起きない (間に動くのはタイマの tick だけで、tick が
  立てる理由は上で全部見分けられる)。
- 試験の道具は、命令ごとの hook から `mrb_checkpoint_request_here()` で要求する。その境目がセーフポイントなら
  その場で書くので、間に何も実行されず、スケジューラの様子は正確 (P3 は「次の境目」で、間に 1 命令
  あった)。例外が飛んでいる途中だけは、捕まえた後の最初のセーフポイントまで待つ (P3 と同じ)。

### 読む側 (C)

- コンテキストを組み立てる: root は今の `root_c` を使い、Task のコンテキストは組み立てた `mrb_task` の中、Fiber の
  コンテキストは新しく確保して Fiber のオブジェクトに結ぶ。
- Task: オブジェクトは mruby-task の型 (static なので、Task を 1 つ作ってすぐ外して型を得る) の
  C のデータとして作り、`mrb_task` を組み立てて、4 つのキューをイメージの順に直接つなぐ (優先度で並べ直す
  `mrb_task_q_insert` は使わない: 待ちキューは優先度順とは限らない)。main の Task は
  `mrb->task.main_task`。全部の Task のオブジェクトを GC のルートに登録する (mruby-task と同じ)。
- 時計: 新しい VM の tick を書いたときの tick にし、起きる時刻は tick + 残り。
- 続け方 (`mrb_checkpoint_continue`): 実行中だった Task が無ければ、今のコンテキスト (root か Fiber) から
  `mrb_vm_exec`。あれば、mruby-task の `execute_task` と同じ手順 (タイムスライスを満タンに、
  RUNNING に、`mrb_vm_exec` を例外を値にして、終わった後の扱い) を、今のコンテキストから始める形で行う
  (mruby-task の `execute_task` は Task 自身のコンテキストからしか始められず、Task の中の Fiber で止まった
  イメージを続けられないため。`checkpoint_task.c` に、`execute_task`・`wake_up_join_waiters`・
  `task_run_body` の後の round robin を写した)。その後、`Task.run` なら呼んだ側の pc を呼び出しの
  命令に戻して呼び出しをやり直し、`Task.pass` なら nil を返して root を続け、埋め込む側なら
  `mrb_task_run` を呼ぶ。

### 埋め込む側の Task

アプリの本体の Task (C の側が `mrb_create_task` で作るもの) は、普通の Task と同じに運ぶ (親の
仮決めのとおり)。イメージには「どれが埋め込む側の Task か」を記す (`mrb_checkpoint_set_host_task`)。
復元した側は `mrb_checkpoint_host_task()` で引いて、値 (捕まえなかった例外など) を見る。
`checkpoint run --as-task` と試験の道具はこれで、プログラムの例外を出す。

## 仮決めの妥当さ (実装してみて)

| 仮決め | 実装してみて |
|---|---|
| 起きる時刻は残りの tick で運び、着いた先の今の tick に足す | そのとおりに書いた。ただし、プログラムが tick の値そのものを持っていることがあった: `Task::Queue#pop` (mrblib、Ruby) は期限を絶対の tick でローカル変数 `deadline` に持ち、`__pop_try` に渡す。着いた先の tick が違うと、その期限が狂う。新しい VM に復元するので、着いた先の tick を書いたときの tick にした (残りの tick は変わらず、移動にかかった時間は待ちに含めない、`Task.tick` の差もつながる)。§サブの仮決め 1 |
| 走っていた Task のタイムスライスは、着いた先で満タンから | そのとおりにした。tick が時間でしか進まない (仮想の時計で `--quantum` なし) 試験では、違いは出ない。`--quantum 300` (300 命令ごとに tick) でタイムスライスを尽きさせると、満タンからにしたことで横取りの位置がずれ、試験一式の Task の形で 2 ファイルが往復なしと違った (§試験の数字)。どちらも、mruby-task の不具合 (Task の中で Fiber が横取りされると、その Task が DORMANT にされる) に当たるかどうかが、位置のずれで変わったもの。残りのタイムスライスを運ぶ切り替え (`mrb_checkpoint_keep_timeslice`) を付けると 0 になる。満タンは実害の無い選び方だが、正確さを取るなら残りを運ぶほうが筋がよい (イメージには残りを書いてある)。決めてほしいこと 1 |
| アプリの本体の Task も普通の Task と同じに運ぶ。ドライバが Task を作り直し、スケジューラを回し直す | 運び方は普通の Task と同じでよかった。ただ、作り直すのは読む側 (C の関数のフレームを作り直すのと同じ) で、ドライバは `mrb_checkpoint_continue` を呼ぶだけになった。ドライバが要るのは「どれが本体の Task か」で、それをイメージに記す API を足した |

## サブの仮決め

1. **着いた先の時計を、書いたときの tick にする** (上の表)。プログラムが絶対の tick を持つため。
   形式には tick と残りの両方を書いてあり、時計を動かせない読み込み側は残りで引き直せる。
2. **`mrb_bool` のフラグの代わりに、スケジューラの様子の差で見分ける** (§スケジューラのフラグ)。VM の
   patch を変えずに済む。外からの要求と 1 命令の `Task.pass` が重なると pass が失われる (止まりは
   しない)。VM に専用のフラグを足す案は、命令の境目ごとの読み込みが 1 つ増え、普段の速さの条件に
   響くので採らなかった。
3. **試験の道具は、その境目で書く** (`mrb_checkpoint_request_here`)。P3 の「次の境目で書く」は、
   間の 1 命令がスケジューラを動かすとイメージの様子が曖昧になる。点の位置が 1 命令ずれるが、点の
   選び方は試験の道具の側のこと。
4. **Task のタイムスライスの続きは、`execute_task` を写して行う**。mruby-task の `execute_task` は
   Task 自身のコンテキストからしか始められない。写しは `checkpoint_task.c` にあり、mruby-task を上げる
   ときに追従が要る (`checkpoint_bundled.c` と同じ扱い)。
5. **`Task.run` の続きは、呼び出しをやり直す** (呼んだ側の pc を呼び出しの命令に戻す)。C の関数を
   C から呼び直すと、そこから出る例外が呼んだ側の rescue に届かないため。キーワード引数を詰めた
   呼び出しなどレジスタが変わる形は、やり直せないので断る (実際には現れない)。
6. **main の Task の名前と戻り値は書かない**。mruby-task がそれを GC から守っておらず (main の Task は
   どのキューにもいないのでマークされない)、試験一式の中で回収済みのものを指していた (Proc や別の
   String に化けた)。読む側は `Task.current` と同じく `"main"` にする。
7. **C の側の GC のルート (`_gc_root_`) を書かない**。mruby-task が Task を登録する所で、v0 の形では
   グローバル変数・permanent な Array の中身の変更として運ばれてしまう。読む側のスケジューラが登録し直す。
8. **終了した Task のスタック上の Env** (mruby-task は Task が終わっても切り離さない) は、C のリーダーは
   そのまま組み立て、SabiRuby はイメージの値で切り離す。
9. **SabiRuby の試験のイメージを 91 個 (約 240 KB) にした** (P2 の決めは 29 個・約 55 KB)。Task・Fiber の
   サンプルと、Task の形のイメージを足した。多ければ Task の形を減らせる。
10. **`refuse.rb` を作り直した**。Fiber の中の suspend は運べるようになったので、断る例を「Fiber の
    中で C の関数 (`sort`) が呼んだブロック」に替えた。理由の文言にコンテキストの番号が出るので、Task の
    形では流さない。
11. **サンプルの sleep は整数のミリ秒** (`sleep_ms`)。`sleep 0.06` は 32bit 版 (x87) で 59 ms になり、
    64bit 版と起きる tick が違う (mruby の側の差。§見立てと違った点)。

## 上流の不具合 (mruby-task・mruby-fiber、f56d44ecc)

どれも checkpoint なしで起きる。直していない (mruby-task・mruby-fiber の振る舞いを変える
ことになるので、止まる条件の側)。

| # | 起きること | 仕組み | ここでの扱い |
|---|---|---|---|
| U1 | Task の中で `Fiber.current` を呼ぶと (`Enumerator#next` が呼ぶ)、`mrb_close` で `free(): invalid pointer` | その Fiber のコンテキストは `mrb_task` の中に埋め込まれたコンテキストなのに、Fiber が回収されるとき `mrb_free_context` がそれを解放する | 試験の道具とドライバは、状態を閉じる前にその Fiber をコンテキストから離す (`close_state`)。試験の道具は往復のたびに状態を閉じるので、手当てしないと毎回落ちた |

| U5 | Task の中の `Fiber#transfer` で、Task の残りが走らない (`fiber.rb` を Task の形で流すと、試験の補助が「途中で止まった」と abort する) | transfer で Fiber のコンテキストになったままフラグが立つと、VM が Task の途中で戻る | そのまま運ぶ (往復なしでも同じく abort する) |

## SabiRuby との違い

| 項目 | C mruby + mruby-task | SabiRuby | 読み込み側でしたこと |
|---|---|---|---|
| コンテキストの切り替えの値 | 待っているコンテキストのいちばん上の C の関数のフレームの窓の始まりに、戻ってきた側が書く | コンテキストの `pending_reg` に書く | その C の関数のフレームはフレームにせず、窓の始まりを `pending_reg` に |
| 未開始の Fiber | ブロックのフレームと、その写しの 2 枚 | フレームを持たず、resume でブロックを並べる | 2 枚とも pc 0 の Fiber は `Created` でフレームなし |
| Task のコンテキストの状態 | 動いた後も「未開始」 | 動けば変わる | Task のコンテキストは `Suspended` |
| 終了した Task のコンテキスト | 最後のフレームと Env (スタック上のまま) を残す | 空にして Env を切り離す | イメージの値で切り離す |
| Task のタイムスライスの続き | `execute_task` は Task 自身のコンテキストからだけ | 同じ | どちらのリーダーも、`execute_task` と同じ手順を今のコンテキストから始める関数を持つ (SabiRuby は `ext_task::checkpoint_slice`) |
| `Task.run` の続き | C の関数 (C のフレーム) | ネイティブの関数 (フレームなし。入れ子の実行ループ) | どちらも呼び出しをやり直す |
| tick | タイマ (4 ms)。試験のビルドは仮想の時計 | 命令の数 (10,000 命令で 1 tick)。空けば次の起きる時刻へ飛ぶ | 時計を書いたときの tick にする。待ちは残りの tick |
| 期限の過ぎた Task が起きる時 | 次の tick | 次の tick (命令の数で来る) | そのまま。仮想の時計で tick が空いたときにだけ進む試験とは、起きる時が違いうる (サンプル `task_suspend` は、出力がそれに依らない形にした) |
| Task の中の `Fiber#transfer` | できる | FiberError (イメージに関係なく) | `fiber_nested` の Task の形は SabiRuby で流さない |
| main の Task | 名前と値を GC から守らない (U4) | 守る | 名前は `"main"` |
| 断るもの | 書く側で、C の関数のフレーム | 書き出し側が書かないので来ない。P3 で未対応の種類 (16〜24) は「まだ運ばない」と断る (残件) | |

## 除外した試験と理由

`test/fuzz_exclude.txt` に足したもの (P3 の 3 つはそのまま)。条件に「Task の形だけ」(`as-task`) と
「SabiRuby で続けるときだけ」(`sabiruby`) を足した:

| 試験 | 条件 | 理由 |
|---|---|---|
| `core/kernel.rb` の `Kernel#hash` | 同じプロセスでも | `hash` を 2 回呼んで比べる。`Kernel#hash` はアドレスから作り、復元した状態の main は別のアドレスの別のオブジェクト (P3 の `Proc#hash` と同じ種類。点の位置が 1 命令ずれて当たるようになった) |
| `mruby-object-ext/object.rb` の `instance_exec on primitives ...` | Task の形だけ | U2。往復なしでも落ちる (未定義の動き)。落ちた後の読み先がメモリの並びで変わる |
| `mruby-io/file.rb` の `File` | 別のプロセスのときだけ | `File#initialize` (mruby-io の mrblib) が `IO.sysopen` の記述子を Integer で持ってから `super` に渡す。その間のイメージは番号を運ぶが、別のプロセスではその番号は別のファイルか何も無い (P3 の `io.rb` と同じ種類) |
| `mruby-io/file_test.rb` の `FileTest` | 別のプロセスのときだけ | `IO.new(IO.sysopen(...))` の 2 つの呼び出しの間のイメージが、記述子の番号を運ぶ (同じ種類)。P3 では、子のプロセスが親から継いだ試験の道具の記録の記述子にたまたま当たって通っていた (§見つけた食い違い 7) |
| `core/array.rb` の `Array#hash` | SabiRuby で続けるときだけ | 等しい Array の `hash` を 2 回呼んで比べる。1 回目は C mruby、2 回目は SabiRuby が計算すると、ハッシュの関数が違う (ハッシュの値は計算した VM のもの) |

除外の表の照合は、試験の行に加えて、終わりの失敗のまとめの行 (`TypeError: <試験の名前> => ...`) も
その試験のものと数えるようにした (U2 の落ち方が、まとめの行で初めて違うことがあるため)。

## 残件 (P5 で見せるのに要る情報)

- イメージから読める、見せたいもの: コンテキストの表 (どれが root・Task・Fiber か、状態、prev のチェーン、今のコンテキスト、
  Fiber のオブジェクトとの対応)、コンテキストごとのフレーム (待っている C の関数の名前を含む)、Task の表 (キューと順、
  状態、優先度、待ちの理由と残りの tick、join・Queue の相手、実行中だった Task、スケジューラを入れた
  側)、Env がどのコンテキストのスタックにあるか。形式に全部ある。
- 行番号: `DBG0` は運ぶ irep だけ。mrblib のフレーム (種類 15 / irep の種類 2) には行番号が無いので、P5 で
  mrblib のフレームの行を出すなら、それらも `DBG0` に入れる (形式は変えずに書く側を広げられる)。
- タイムスライスを満タンにするか残りを運ぶか (決めてほしいこと 1)。
- 外からの要求と `Task.pass` が 1 命令で重なると pass が失われる (§スケジューラのフラグ)。Family mruby に
  持ち込むとき、外からの要求を割り込みでどう出すかと合わせて決める。
- `checkpoint_task.c` の `execute_task` などの写しは mruby-task に追従が要る。Family mruby の
  mruby-task には自前の patch があるので、持ち込むときに差を見る。
- 上流の不具合 U1〜U5。
- SabiRuby: P3 の種類 16〜24 と変更表の 8・9 (Hash の中身の 10) はまだ運ばない。

## 決めてほしいこと

1. **タイムスライス**: 着いた先で満タンから (親の仮決め、今の既定) か、残りを運ぶ (イメージには書いてあり、
   切り替え `mrb_checkpoint_keep_timeslice` で動く) か。満タンでは、横取りの位置が往復なしとずれる
   (`--quantum` の Task の形で 2 ファイル。mruby-task の U3 と組み合わさったとき)。残りを運ぶと 0。
   どちらも害は無い。おすすめは残りを運ぶ (同じイメージから何度復元しても同じ動き、という「残りの tick」の
   考え方とそろう)。
2. **着いた先の時計を書いたときの tick にすること** (サブの仮決め 1)。Family mruby で、復元する VM が
   既に動いている (ほかのアプリと時計を共有する) なら、この形は取れず、プログラムが持つ絶対の tick
   (`Task::Queue#pop` の期限) が狂う。持ち込むときの形 (アプリごとに VM か) と合わせて決める。
3. **上流の不具合 U1〜U5** を mruby (mruby-task・mruby-fiber) に報告するか。どれも checkpoint なしで
   起きる。
4. **外からの要求で `Task.pass` が失われうること** (サブの仮決め 2) をこのまま認めるか。VM の patch に
   専用のフラグを足せば消えるが、命令の境目ごとの読み込みが 1 つ増える。
5. **SabiRuby の試験のイメージを 91 個 (約 240 KB) にしたこと** (P2 の決めは 29 個・約 55 KB)。
