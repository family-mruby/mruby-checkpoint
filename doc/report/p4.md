# P4 報告: Task と Fiber、形式 v1、Family mruby と同じ起動の形

> 状態: 実装済・検収待ち | 更新: 2026-11-03 | 指示は `doc/instruction_p4.md`

## 結果

- 形式を v1 にした (`doc/format_v1.md`)。VM の部分が、実行の文脈の表 (root・Task ごと・Fiber
  ごとのスタックと呼び出しの枠と状態)、今の文脈、スケジューラ (Task を列の順に、時計、待ちの
  残りの tick) になった。Task と Fiber はオブジェクトの種類 26・27、Task::Queue は C のデータの
  別表の項目として運ぶ。行番号の節 `DBG0` ほか P3 の追補はそのまま正式の節にした。
- Fiber の中・Task の中・Task が待っている最中・Task の中の Fiber の中で、書き出して続けられる。
  断るのは C の関数の枠 (C のスタックにあるもの) だけになった。
- `checkpoint run --as-task` (プログラムの本体を Task にして `mrb_task_run`。Family mruby の
  アプリの起動の形) を足した。サンプルの試験と試験一式の外からの停止は、両方の形で流す。
- 試験のビルド (`build/fuzz`) の mruby-task を仮想の時計にした (`mrbgems/hal-task-virtual`)。
  tick はスケジューラが空いたときと root が sleep したときに進み、`--quantum N` で N 命令ごとにも
  進む。普段のビルドは今の POSIX のタイマのまま。
- 長い版 (種 1〜20、1 ファイル約 200 点、P3 と同じ規模) で、往復なしと食い違った実行は、除外の
  表の正当な違いを除いて **0** (top-level の形・Task の形とも)。P3 で断っていた Fiber・Task に
  関わる 5 つの理由 (P3 の長い版で 18,901 点) は **0** になった。残る Fiber・Task 関係の断りは、
  C の関数が yield した Fiber が待っている場合 (C の枠。原理的に運べない) だけ。
  (数字は §試験の数字)
- SabiRuby の読み手を v1 に合わせ、Fiber と Task を組み立てて続けるようにした (片道)。
  サンプルの像は両方の形ですべて SabiRuby でも続き、出力が一致する。
- 復元の後に例外を起こすと、バックトレースの行番号が往復なしと一致する (`lines.rb`: root・
  Fiber・Task で、64 ⇔ 32、別のプロセス、Task の形、SabiRuby)。
- 普段のビルドの `vm.c` の patch は変えていない (valgrind の命令数の比較はしていない)。
- 調べる途中で、mruby-task・mruby-fiber 自身の不具合を 5 つ見つけた (§上流の不具合)。直して
  いない (止まる条件: mruby-task の作りや振る舞いを変えることになる)。試験の道具と除外の表で
  扱いを決めた。

## v1 で足したもの

`doc/format_v1.md` §16 に一覧。要点:

- **実行の文脈の表** (§10): 文脈ごとに状態 (作っただけ・動いている・resume して待っている・
  止まっている・transfer して待っている・終わった)、prev (resume した文脈)、Fiber のオブジェクト、
  スタック、枠。root が 1 番、Task の文脈が続き、Fiber の文脈は届いた順。
- **枠の種類**: Ruby の枠に加えて「文脈の切り替えを待っている C の関数の枠」(`Fiber#resume`・
  `Fiber#transfer`・`Fiber.yield`・`Task.run`・`Task.pass`)。待っている文脈のいちばん上にだけ現れ、
  関数の名前を持つ。呼び出しの値は、切り替えで戻ってきた側がその窓の始まりに入れる。
- **スタック上の Env** は文脈の番号を持つ。
- **スケジューラ** (§11): 切り替えの頼み、輪が回っていたか、1 tick のミリ秒、tick、次に起きる
  時刻の残り、Task (列ごとに列の順。状態・列・優先度・待ちの理由と中身・名前・戻り値・時間の
  割り当ての残り)、動いていた Task、埋め込む側の Task。
- **Task::Queue**: C のデータの別表の項目 (閉じているか)。中身は ivar `@items`、待っている Task は
  Task の表が Queue のオブジェクトを指す。
- **続け方** (§12): 読む側が何を始め直すかを、形式の一部として書いた。

## Task・Fiber の運び方

### 書く側

- 安全点の hook は、P1 からの patch のまま、Task の文脈の中でもスケジューラへ戻る前に呼ばれて
  いた (判定の `task_stop_requested` が hook を先に呼ぶ)。v1 では、どの文脈にいても書く。
- 書くのは、root、列にいる全部の Task の文脈、今の文脈、そこから届く文脈 (Fiber のオブジェクト、
  prev、スタック上の Env の文脈)。文脈とオブジェクトは互いに届くので、両方の待ち行列が空になる
  まで交互に書く。
- 全部の文脈の全部の枠を見て、C から入った枠 (cci が 0 でない)・待っている文脈のいちばん上
  以外の C の関数の枠・表に無い C の関数で待っている文脈・C から resume された Fiber (vmexec) を
  断る。Task の文脈の vmexec は、動いている Task では立っているのが正しい (スケジューラの C の枠は
  読む側が作り直す)。
- 動いていた Task は、今の文脈から prev をたどって最初に当たる Task の文脈の持ち主 (無ければ
  ready の列で RUNNING のもの)。自分を止めた Task は、その境目でもう DORMANT のことがある。
- スケジューラを入れた側 (動いていた Task の文脈の prev) は、`Task.run`・`Task.pass` の C の
  関数の枠か、枠の無い root (埋め込む側が C から `mrb_task_run`) でなければ断る。
- 時刻は書いたときの tick と、各待ちの残りの tick (期限 − tick) で書く。

### スケジューラの印

`task.switching` はスケジューラの印でもあり、しかも C の bool で、要求が立てた後にスケジューラも
立てたかを後から見分けられない (2 などの別の値を入れる案は、bool なので成り立たなかった)。そこで:

- 要求は、印がもう立っていればそのまま (スケジューラの頼みがある)、立っていなければ立てて、
  そのときのスケジューラの様子 (動いている Task、待ちの列と理由、準備の列) を控える。
- 安全点では、控えとの差で、スケジューラが間に切り替えを頼んだかを決める: 動いていた Task が
  もう RUNNING でない・止められた・時間の割り当てが尽きた、待っていた Task が起きた (join の待ちは
  mruby-task と同じく優先度が上のときだけ)、優先度が上の Task が準備の列に入った。頼んでいれば
  印を残し (VM はすぐスケジューラへ戻る)、像には「その境目で割り当てが終わる」と書く。頼んで
  いなければ印を消して続ける。
- 見分けられないのは、外からの要求と安全点の間の 1 命令が `Task.pass` だった場合だけ (印を立てる
  ほかに何もしない)。その pass は失われ、Task は割り当てが尽きるまで続く (止まることはない)。
  `Checkpoint.save` の呼び出しの中ではこれは起きない (間に動くのはタイマの tick だけで、tick が
  立てる理由は上で全部見分けられる)。
- 試験の道具は、命令ごとの hook から `mrb_checkpoint_request_here()` で頼む。その境目が安全点なら
  その場で書くので、間に何も実行されず、スケジューラの様子は正確 (P3 は「次の境目」で、間に 1 命令
  あった)。例外が飛んでいる途中だけは、捕まえた後の最初の安全点まで待つ (P3 と同じ)。

### 読む側 (C)

- 文脈を組み立てる: root は今の `root_c` を使い、Task の文脈は組み立てた `mrb_task` の中、Fiber の
  文脈は新しく確保して Fiber のオブジェクトに結ぶ。
- Task: オブジェクトは mruby-task の型 (static なので、Task を 1 つ作ってすぐ外して型を得る) の
  C のデータとして作り、`mrb_task` を組み立てて、4 つの列を像の順に直接つなぐ (優先度で並べ直す
  `mrb_task_q_insert` は使わない: 待ちの列は優先度順とは限らない)。main の Task は
  `mrb->task.main_task`。全部の Task のオブジェクトを GC の根に登録する (mruby-task と同じ)。
- 時計: 新しい VM の tick を書いたときの tick にし、起きる時刻は tick + 残り。
- 続け方 (`mrb_checkpoint_continue`): 動いていた Task が無ければ、今の文脈 (root か Fiber) から
  `mrb_vm_exec`。あれば、mruby-task の `execute_task` と同じ手順 (時間の割り当てを満タンに、
  RUNNING に、`mrb_vm_exec` を例外を値にして、終わった後の扱い) を、今の文脈から始める形で行う
  (mruby-task の `execute_task` は Task 自身の文脈からしか始められず、Task の中の Fiber で止まった
  像を続けられないため。`checkpoint_task.c` に、`execute_task`・`wake_up_join_waiters`・
  `task_run_body` の後の round robin を写した)。その後、`Task.run` なら呼んだ側の pc を呼び出しの
  命令に戻して呼び出しをやり直し、`Task.pass` なら nil を返して root を続け、埋め込む側なら
  `mrb_task_run` を呼ぶ。

### 埋め込む側の Task

アプリの本体の Task (C の側が `mrb_create_task` で作るもの) は、普通の Task と同じに運ぶ (親の
仮決めのとおり)。像には「どれが埋め込む側の Task か」を記す (`mrb_checkpoint_set_host_task`)。
復元した側は `mrb_checkpoint_host_task()` で引いて、値 (捕まえなかった例外など) を見る。
`checkpoint run --as-task` と試験の道具はこれで、プログラムの例外を出す。

## 仮決めの妥当さ (実装してみて)

| 仮決め | 実装してみて |
|---|---|
| 起きる時刻は残りの tick で運び、着いた先の今の tick に足す | そのとおりに書いた。ただし、プログラムが tick の値そのものを持っていることがあった: `Task::Queue#pop` (mrblib、Ruby) は期限を絶対の tick で局所変数 `deadline` に持ち、`__pop_try` に渡す。着いた先の tick が違うと、その期限が狂う。新しい VM に復元するので、着いた先の tick を書いたときの tick にした (残りの tick は変わらず、移動にかかった時間は待ちに含めない、`Task.tick` の差もつながる)。§サブの仮決め 1 |
| 走っていた Task の時間の割り当ては、着いた先で満タンから | そのとおりにした。tick が時間でしか進まない (仮想の時計で `--quantum` なし) 試験では、違いは出ない。`--quantum 300` (300 命令ごとに tick) で割り当てを尽きさせると、満タンからにしたことで横取りの位置がずれ、試験一式の Task の形で 2 ファイルが往復なしと違った (§試験の数字)。どちらも、mruby-task の不具合 (Task の中で Fiber が横取りされると、その Task が DORMANT にされる) に当たるかどうかが、位置のずれで変わったもの。残りの割り当てを運ぶ切り替え (`mrb_checkpoint_keep_timeslice`) を付けると 0 になる。満タンは実害の無い選び方だが、正確さを取るなら残りを運ぶほうが筋がよい (像には残りを書いてある)。決めてほしいこと 1 |
| アプリの本体の Task も普通の Task と同じに運ぶ。ドライバが Task を作り直し、スケジューラを回し直す | 運び方は普通の Task と同じでよかった。ただ、作り直すのは読む側 (C の関数の枠を作り直すのと同じ) で、ドライバは `mrb_checkpoint_continue` を呼ぶだけになった。ドライバが要るのは「どれが本体の Task か」で、それを像に記す口を足した |

## サブの仮決め

1. **着いた先の時計を、書いたときの tick にする** (上の表)。プログラムが絶対の tick を持つため。
   形式には tick と残りの両方を書いてあり、時計を動かせない読み手は残りで引き直せる。
2. **`mrb_bool` の印の代わりに、スケジューラの様子の差で見分ける** (§スケジューラの印)。VM の
   patch を変えずに済む。外からの要求と 1 命令の `Task.pass` が重なると pass が失われる (止まりは
   しない)。VM に専用の印を足す案は、命令の境目ごとの読み込みが 1 つ増え、普段の速さの条件に
   響くので採らなかった。
3. **試験の道具は、その境目で書く** (`mrb_checkpoint_request_here`)。P3 の「次の境目で書く」は、
   間の 1 命令がスケジューラを動かすと像の様子が曖昧になる。点の位置が 1 命令ずれるが、点の
   選び方は試験の道具の側のこと。
4. **Task の時間の割り当ての続きは、`execute_task` を写して行う**。mruby-task の `execute_task` は
   Task 自身の文脈からしか始められない。写しは `checkpoint_task.c` にあり、mruby-task を上げる
   ときに追従が要る (`checkpoint_bundled.c` と同じ扱い)。
5. **`Task.run` の続きは、呼び出しをやり直す** (呼んだ側の pc を呼び出しの命令に戻す)。C の関数を
   C から呼び直すと、そこから出る例外が呼んだ側の rescue に届かないため。キーワード引数を詰めた
   呼び出しなどレジスタが変わる形は、やり直せないので断る (実際には現れない)。
6. **main の Task の名前と戻り値は書かない**。mruby-task がそれを GC から守っておらず (main の Task は
   どの列にもいないので印が付かない)、試験一式の中で回収済みのものを指していた (Proc や別の
   String に化けた)。読む側は `Task.current` と同じく `"main"` にする。
7. **C の側の GC の根 (`_gc_root_`) を書かない**。mruby-task が Task を登録する所で、v0 の形では
   大域変数・permanent な Array の中身の変更として運ばれてしまう。読む側のスケジューラが登録し直す。
8. **終わった Task のスタック上の Env** (mruby-task は Task が終わっても切り離さない) は、C の読み手は
   そのまま組み立て、SabiRuby は像の値で切り離す。
9. **SabiRuby の試験の像を 91 個 (約 240 KB) にした** (P2 の決めは 29 個・約 55 KB)。Task・Fiber の
   サンプルと、Task の形の像を足した。多ければ Task の形を減らせる。
10. **`refuse.rb` を作り直した**。Fiber の中の suspend は運べるようになったので、断る例を「Fiber の
    中で C の関数 (`sort`) が呼んだブロック」に替えた。理由の文言に文脈の番号が出るので、Task の
    形では流さない。
11. **サンプルの sleep は整数のミリ秒** (`sleep_ms`)。`sleep 0.06` は 32bit 版 (x87) で 59 ms になり、
    64bit 版と起きる tick が違う (mruby の側の差。§見立てと違った点)。

## 上流の不具合 (mruby-task・mruby-fiber、f56d44ecc)

どれも checkpoint なしで起きる。直していない (mruby-task・mruby-fiber の振る舞いを変える
ことになるので、止まる条件の側)。

| # | 起きること | 仕組み | ここでの扱い |
|---|---|---|---|
| U1 | Task の中で `Fiber.current` を呼ぶと (`Enumerator#next` が呼ぶ)、`mrb_close` で `free(): invalid pointer` | その Fiber の文脈は `mrb_task` の中に埋め込まれた文脈なのに、Fiber が回収されるとき `mrb_free_context` がそれを解放する | 試験の道具とドライバは、状態を閉じる前にその Fiber を文脈から離す (`close_state`)。試験の道具は往復のたびに状態を閉じるので、手当てしないと毎回落ちた |
| U2 | Task の中で `1.instance_exec { }` (Integer など特異クラスを持てない物) をすると SEGV | ブロックの枠の定義先のクラスが NULL で、mruby-task が文脈を vmexec にしているため、VM がそれを「文脈の切り替えからの戻り」と読んで Task の途中で `mrb_vm_exec` を抜ける。スケジューラは次にその Task を命令列の終わりの先から動かす | 除外の表 (Task の形だけ)。書く側は、枠が命令列の外に立つ状態を断る |
| U3 | Task の中で Fiber を動かしている最中に時間の割り当てが尽きると、その Task は DORMANT にされる | 割り当ての終わりで VM が Fiber の文脈のまま戻り、Task の文脈のいちばん上は `Fiber#resume` の C の枠 (Proc が無い) なので、`execute_task` が壊れた Task として片付ける | そのまま運ぶ (書いた側と同じことが着いた先でも起きる)。`--quantum` での食い違いの元 (仮決めの妥当さ) |
| U4 | main の Task の名前と戻り値が回収される | main の Task はどの列にもなく、`mrb_task_mark_all` が印を付けない。Data のオブジェクトにも印を付ける関数が無い | 書かない (サブの仮決め 6) |
| U5 | Task の中の `Fiber#transfer` で、Task の残りが走らない (`fiber.rb` を Task の形で流すと、試験の補助が「途中で止まった」と abort する) | transfer で Fiber の文脈になったまま印が立つと、VM が Task の途中で戻る | そのまま運ぶ (往復なしでも同じく abort する) |

## SabiRuby との違い

| 項目 | C mruby + mruby-task | SabiRuby | 読み手でしたこと |
|---|---|---|---|
| 文脈の切り替えの値 | 待っている文脈のいちばん上の C の関数の枠の窓の始まりに、戻ってきた側が書く | 文脈の `pending_reg` に書く | その C の関数の枠は枠にせず、窓の始まりを `pending_reg` に |
| 作っただけの Fiber | ブロックの枠と、その写しの 2 枚 | 枠を持たず、resume でブロックを並べる | 2 枚とも pc 0 の Fiber は `Created` で枠なし |
| Task の文脈の状態 | 動いた後も「作っただけ」 | 動けば変わる | Task の文脈は `Suspended` |
| 終わった Task の文脈 | 最後の枠と Env (スタック上のまま) を残す | 空にして Env を切り離す | 像の値で切り離す |
| Task の割り当ての続き | `execute_task` は Task 自身の文脈からだけ | 同じ | どちらの読み手も、`execute_task` と同じ手順を今の文脈から始める関数を持つ (SabiRuby は `ext_task::checkpoint_slice`) |
| `Task.run` の続き | C の関数 (C の枠) | ネイティブの関数 (枠なし。入れ子の実行の輪) | どちらも呼び出しをやり直す |
| tick | タイマ (4 ms)。試験のビルドは仮想の時計 | 命令の数 (10,000 命令で 1 tick)。空けば次の起きる時刻へ飛ぶ | 時計を書いたときの tick にする。待ちは残りの tick |
| 期限の過ぎた Task が起きる時 | 次の tick | 次の tick (命令の数で来る) | そのまま。仮想の時計で tick が空いたときにだけ進む試験とは、起きる時が違いうる (サンプル `task_suspend` は、出力がそれに依らない形にした) |
| Task の中の `Fiber#transfer` | できる | FiberError (像に関係なく) | `fiber_nested` の Task の形は SabiRuby で流さない |
| main の Task | 名前と値を GC から守らない (U4) | 守る | 名前は `"main"` |
| 断るもの | 書く側で、C の関数の枠 | 書き出し側が書かないので来ない。P3 で未対応の種類 (16〜24) は「まだ運ばない」と断る (残件) | |

## 除外した試験と理由

`test/fuzz_exclude.txt` に足したもの (P3 の 3 つはそのまま)。条件に「Task の形だけ」(`as-task`) と
「SabiRuby で続けるときだけ」(`sabiruby`) を足した:

| 試験 | 条件 | 理由 |
|---|---|---|
| `core/kernel.rb` の `Kernel#hash` | 同じプロセスでも | `hash` を 2 回呼んで比べる。`Kernel#hash` はアドレスから作り、復元した状態の main は別のアドレスの別のオブジェクト (P3 の `Proc#hash` と同じ種類。点の位置が 1 命令ずれて当たるようになった) |
| `mruby-object-ext/object.rb` の `instance_exec on primitives ...` | Task の形だけ | U2。往復なしでも落ちる (未定義の動き)。落ちた後の読み先がメモリの並びで変わる |
| `mruby-io/file.rb` の `File` | 別のプロセスのときだけ | `File#initialize` (mruby-io の mrblib) が `IO.sysopen` の記述子を Integer で持ってから `super` に渡す。その間の像は番号を運ぶが、別のプロセスではその番号は別のファイルか何も無い (P3 の `io.rb` と同じ種類) |
| `mruby-io/file_test.rb` の `FileTest` | 別のプロセスのときだけ | `IO.new(IO.sysopen(...))` の 2 つの呼び出しの間の像が、記述子の番号を運ぶ (同じ種類)。P3 では、子のプロセスが親から継いだ試験の道具の記録の記述子にたまたま当たって通っていた (§見つけた食い違い 7) |
| `core/array.rb` の `Array#hash` | SabiRuby で続けるときだけ | 等しい Array の `hash` を 2 回呼んで比べる。1 回目は C mruby、2 回目は SabiRuby が計算すると、ハッシュの関数が違う (ハッシュの値は計算した VM のもの) |

除外の表の照合は、試験の行に加えて、終わりの失敗のまとめの行 (`TypeError: <試験の名前> => ...`) も
その試験のものと数えるようにした (U2 の落ち方が、まとめの行で初めて違うことがあるため)。

## 残件 (P5 で見せるのに要る情報)

- 像から読める、見せたいもの: 文脈の表 (どれが root・Task・Fiber か、状態、prev の鎖、今の文脈、
  Fiber のオブジェクトとの対応)、文脈ごとの枠 (待っている C の関数の名前を含む)、Task の表 (列と順、
  状態、優先度、待ちの理由と残りの tick、join・Queue の相手、動いていた Task、スケジューラを入れた
  側)、Env がどの文脈のスタックにあるか。形式に全部ある。
- 行番号: `DBG0` は運ぶ irep だけ。mrblib の枠 (種類 15 / irep の種類 2) には行番号が無いので、P5 で
  mrblib の枠の行を出すなら、それらも `DBG0` に入れる (形式は変えずに書く側を広げられる)。
- 時間の割り当てを満タンにするか残りを運ぶか (決めてほしいこと 1)。
- 外からの要求と `Task.pass` が 1 命令で重なると pass が失われる (§スケジューラの印)。Family mruby に
  持ち込むとき、外からの要求を割り込みでどう出すかと合わせて決める。
- `checkpoint_task.c` の `execute_task` などの写しは mruby-task に追従が要る。Family mruby の
  mruby-task には自前の patch があるので、持ち込むときに差を見る。
- 上流の不具合 U1〜U5。
- SabiRuby: P3 の種類 16〜24 と変更表の 8・9 (Hash の中身の 10) はまだ運ばない。

## 決めてほしいこと

1. **時間の割り当て**: 着いた先で満タンから (親の仮決め、今の既定) か、残りを運ぶ (像には書いてあり、
   切り替え `mrb_checkpoint_keep_timeslice` で動く) か。満タンでは、横取りの位置が往復なしとずれる
   (`--quantum` の Task の形で 2 ファイル。mruby-task の U3 と組み合わさったとき)。残りを運ぶと 0。
   どちらも害は無い。おすすめは残りを運ぶ (同じ像から何度復元しても同じ動き、という「残りの tick」の
   考え方とそろう)。
2. **着いた先の時計を書いたときの tick にすること** (サブの仮決め 1)。Family mruby で、復元する VM が
   既に動いている (ほかのアプリと時計を共有する) なら、この形は取れず、プログラムが持つ絶対の tick
   (`Task::Queue#pop` の期限) が狂う。持ち込むときの形 (アプリごとに VM か) と合わせて決める。
3. **上流の不具合 U1〜U5** を mruby (mruby-task・mruby-fiber) に報告するか。どれも checkpoint なしで
   起きる。
4. **外からの要求で `Task.pass` が失われうること** (サブの仮決め 2) をこのまま認めるか。VM の patch に
   専用の印を足せば消えるが、命令の境目ごとの読み込みが 1 つ増える。
5. **SabiRuby の試験の像を 91 個 (約 240 KB) にしたこと** (P2 の決めは 29 個・約 55 KB)。
