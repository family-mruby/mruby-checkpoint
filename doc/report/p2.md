# P2 報告: mruby → SabiRuby の片道

> 状態: 実装済・検収待ち | 更新: 2026-11-02 | 指示は `doc/instruction_p2.md`

## 結果

- C mruby (64bit・32bit) が `Checkpoint.suspend` / `Checkpoint.save` で書いた像を、
  SabiRuby が読んで呼び出しの次の命令から続ける。続きの出力は往復なしの基準と一致する。
- 試験のサンプル 13 本のうち、像を作る 12 本で、鎖の各点の像 (2 回以上 suspend するものは
  各点) を 64bit・32bit の書き手で作り、SabiRuby で続けた。11 本はすべての点で一致、
  `sabiruby_refuse` (新) は 2 点とも理由を出して断る (意図どおり)。`refuse` は書き出し側で
  断るので像が無い。
- `times`・`each_with_index`・`each` のブロックの中 (mrblib の枠) も続く。枠が動かしている
  mrblib の irep は中身ごと運ぶようにした (§選んだ方式)。
- SabiRuby 側は feature `checkpoint` (既定 off) の下に置いた。off のビルドにはコードが
  入らない。SabiRuby の試験は off・on の両方で通り、`tools/check_no_std.sh` も両方で通る。
- 止まる条件には当たらなかった。SabiRuby の VM の中心 (命令の実行・GC・Value) は変えて
  いない。足したのは feature の下のモジュールと、`src/vm.rs` の cfg 付きの関数 1 つ
  (組み立てた枠を `run_loop(0)` で動かす) だけ。

## 選んだ方式と理由

### mrblib の irep: 表に入るものは常に中身ごと運ぶ

指示は「止まっていたフレームが指す mrblib の irep だけ中身も運ぶ」。書き出しでは:

- 枠の Proc が mrblib のメソッドの Proc (名前の付いた permanent) なら、オブジェクトを
  種類 15 (名前 + irep の番号) で書き、その irep を表に入れる。
- 表に入る permanent な irep は、種類 2 (ハッシュ + 中身) で書く。permanent な irep が表に
  入るのは、枠が動かしているとき、実行中に作られた Proc (mrblib の中のブロック、
  `each_with_index` の中の `each { }` のブロックなど) が持っているとき、その子のときだけ。
  他の mrblib のメソッドは今までどおり名前で結ぶ。

「必要な時だけ」か「常に」かは、**常に**にした。

- 書く側は、誰が読むかを知らない。同じビルドの C mruby は種類 2 をハッシュで自分の irep に
  結び、中身を読み飛ばすので、P1 までの往復は何も変わらない (`rake test` の C の項目は
  すべて前と同じく通る)。
- 増える大きさは mrblib の枠があるときだけで、試験の像で 59〜254 バイト
  (`Integer#times` 1 つで 93 バイト。`block` の 2 点目は 3 つで 254 バイト)。
- 切り替えにすると、「SabiRuby に渡すつもりで切り替えを忘れた像」が SabiRuby で断られる
  だけの事故が起きる。小さいので常に運ぶほうが単純。

SabiRuby は種類 15 を読むと、運ばれた irep を本体とする Proc を新しく作って枠に使う
(持ち主のクラスは名前から、strict と scope を立てる)。名前で SabiRuby の `Integer#times` に
結ぶと、そちらは 4.1.0-rc2 の mrbc で作られた別の命令列で、pc が合わない。

### 形式の版: v0 のまま

足したのは irep の種類 2 とオブジェクトの種類 15 だけで、並びは変えていない。P1 の読み手は
知らない種類を「bad irep kind」「bad object kind」で断るので、黙って読み違えることはない。
P1 の像を外に出した所も無い。版を上げると文書の名前 (`format_v0.md`) から変わり、得る
ものが無いので上げなかった。上げるかどうかは決めてほしいこと (下) に入れた。

### 名前の対応: 表ではなく、名前を引く手順

`checkpoint names` で書き出し側の名前 1554 個を出せるようにしたが、SabiRuby には対応の表を
置かなかった。名前は「Object からどうたどるか」で付いているので、SabiRuby も同じ道を
自分のクラスでたどれば引ける (`T`、定数の道筋、`S:`・`I:`・`M:`・`F:`・`E:`・`V:`・`G:`)。
表にすると C mruby の gembox を変えるたびに作り直しになる。一覧は、引けるかどうかを
確かめる材料として使う (`sabiruby --checkpoint-names`)。

メソッド表の項目は、C で書かれたもの (`F:`) も、C mruby では Ruby・SabiRuby では Rust の
もの (`M:`) も、SabiRuby の同じ名前のメソッドに結ぶ (Native でもそのまま)。Proc そのものが
値として要るときだけ断る。`attr_reader`・`attr_writer` が作る C mruby の Proc (C 関数 +
ivar の名前を持つ Env) は、SabiRuby の属性メソッド (`Method::AttrReader` など) に置き換える。

### SabiRuby の Checkpoint.save / suspend は書き出さない

逆向きはこの段の外なので、SabiRuby の `save` / `suspend` は何も書かず、書き出し側の基準の
実行 (`--ignore`) と同じ値を返す (`save` は `:saved`、`suspend` は `:resumed`)。2 回 suspend
する `counter` は、1 点目の像から SabiRuby で最後まで動く。Fiber の中で頼んだときの断りは
書き出し側と同じ文言にした。`Checkpoint.resumed?` は像から復元した VM で真。
`Checkpoint::Box` は Data の handle に値を持たせた (C のデータの別表の SabiRuby 側の 1 例)。

## SabiRuby に足した口

| 口 | 中身 |
|---|---|
| `Vm::checkpoint_resume(&mut self, &[u8]) -> VmResult<Value>` | 組み立てて最後まで動かす。断るときは `Checkpoint::Error` ("restore failed: 理由") |
| `Vm::checkpoint_install` | `Checkpoint` モジュールを定義する (resume が最初に呼ぶ) |
| `Vm::checkpoint_name` | 名前 1 つが何に当たるか |
| `Vm::checkpoint_header` | 形式の版と書き手の名前 |
| `Vm::checkpoint_run` (`pub(crate)`、`src/vm.rs`) | 組み立てた枠を `run_loop(0)` で動かす。`run_irep` の後半と同じ |
| `sabiruby --resume IMAGE` | `run` と同じ VM (mrblib、空の ARGV) で resume |
| `sabiruby --checkpoint-names FILE` | `checkpoint names` の出力を読み、名前ごとに ok / missing と理由 |

内部の型 (`VmIrep`・`CallInfo`・`EnvData`・`ProcData`・`ClassData`・`Heap::alloc`) は crate の
中の今の公開範囲で使えた。公開範囲を広げた所は無い。

写し方の要点 (詳しくは SabiRuby の `docs/plans/checkpoint-plan.md`):

| 像 | SabiRuby |
|---|---|
| 枠の `nk` | `kw` = `nk == 15`。ENTER の後は 0 か 15 なので足りる。1〜14 は断る |
| 枠の `cci` | いちばん下は `Cci::Skip` (`run_irep` と同じ。`run_loop(0)` がそこで戻る)、他は `Cci::None` |
| 枠の渡されたブロック (`ci->blk`) | 使わない。ブロックのレジスタにも同じものがあり、SabiRuby はそこを読む |
| 枠の pc | そのまま。SabiRuby も「いちばん上は次の命令、下は呼び出しの次」 |
| スタック上の Env | `attached`、`base` = 位置、`ctx` = ROOT。位置がどれかの枠の始まりでその枠の環境であることを確かめる |
| クラスの ivar の表 | 定数 → `consts`、`@@x` → `cvars`、`__classname__` → `name` (+ パスなら `outer`)、`__attached__` → `attached` |
| 取り込みクラス | `ClassData { iclass_of }` |
| Hash の既定値 (ivar `ifnone`) | 既定値は `default`、既定の Proc は ivar `__default_proc` |
| Exception のバックトレース (文字列の配列) | ivar `@__btstr` (`set_backtrace` と同じ置き場) |
| クラスの無いオブジェクト (C の Proc、C 関数が作る内部の Array) | 素のクラス |

## 名前の対応の表

書き出し側 (既定の gembox + mruby-task + mruby-checkpoint) の名前 1554 個を
`sabiruby --checkpoint-names` で引いた結果:

| 接頭辞 | 引けた | 無い |
|---|---:|---:|
| クラス・モジュール | 70 | 24 |
| `S:` 特異クラス | 76 | 24 |
| `I:` 取り込みクラス | 13 | 4 |
| `M:` Ruby のメソッドの Proc | 334 | 107 |
| `F:` C の関数 | 712 | 143 |
| `E:` その Env | 0 | 13 |
| `V:` クラスが持つ値 | 19 | 13 |
| `X:` 前もって作る例外 | 0 | 2 |
| 計 | 1224 | 330 |

- 無い 330 個のうち 309 個は、SabiRuby に無い POSIX の gem (io・socket・dir・errno、`ENV`、
  `STDOUT` など) のもの。
- `M:` の引けた 334 個のうち 28 個は、SabiRuby では Rust のメソッド (`Kernel#puts` など
  mruby-io が Ruby で書き直すもの、`String#gsub` など)。メソッド表の項目としては結べる。
- 残り 21 個: C mruby の内部の補助 (`Kernel#__to_int`、`Regexp#__sub_str` など 8 個)、
  `attr_reader` で作られた Proc の Env (`E:NameError#name` など 7 個。SabiRuby では属性
  メソッドで Env が無い)、`NoMemoryError` とその特異クラス、`V:Random@mruby_Random`、
  `F:S:T#define_method`、`X:nomem_err`・`X:stack_err`。
- `V:<クラス>@__classname__` (入れ子のクラスの名前の文字列) は、SabiRuby ではクラスから
  名前の文字列を作って当てる (同じ値、別のオブジェクト)。

試験のサンプルの像が指す permanent は、すべて引けた。

## 命令の差 (4.0 系 ↔ 4.1.0-rc2)

| 項目 | 結果 |
|---|---|
| 命令の表 (`include/mruby/ops.h`) | 119 個とも名前・順・オペランドの形が同じ (`kishima/mruby:4.1.0-rc2` の ops.h と diff) |
| 例外処理の表の 1 行 (13 バイト)、プールの種類 | 同じ |
| ENTER の後の `n`・`nk` の意味 | 同じ (`nk` は 0 か 15) |
| 枠の pc の意味 | 同じ |
| `Kernel#catch` | 違う。C mruby は bytecode の Proc (`catch_proc`) で、`throw` は枠を遡ってその Proc を探す。SabiRuby の `catch` は native のループ枠で、`throw` はそれを探す。運んだ `catch` の枠は SabiRuby の `throw` に見つからない (試すと `UncaughtThrowError`) → 断る |
| Method オブジェクト | 違う。C mruby の Method は中に C 関数の Proc を持つ。SabiRuby の Rust のメソッドは Proc でない → 断る |

命令の差では困らなかった。困ったのは mrblib・ライブラリの作りの違い (上の 2 つ) だけ。

## 拒否した型・場面

SabiRuby が断るもの (書き出し側が断るものは P1 のまま):

| 場面 | 理由 |
|---|---|
| ハッシュだけの permanent な irep | 中身が要る。P2 の書き手は書かない |
| 運ばれた irep のハッシュが合わない | 壊れている |
| SabiRuby に無い permanent を値として指す | 結ぶ先が無い (POSIX の gem のものなど) |
| C 関数の Proc を値として持つ (Method オブジェクトなど) | Rust のメソッドは Proc でない |
| `Kernel#catch` の枠 | `throw` が見つけられない |
| 型名の分からない C のデータ | 復元の関数が無い (`Checkpoint::Box` だけ持つ) |
| ENTER の前のキーワード引数 (`nk` 1〜14) | SabiRuby の枠はキーワードを Hash 1 つで持つ |
| C から入った枠 | 形式の約束 (書き出し側も書かない) |

## 見立てと違った点

- **ほぼ一度で通った**。最初に組み立てたものが像を作る 11 本 (当時) 中 9 本で一致し、残り 2 本 (builtin_patch・hash) はクラスを
  持たないオブジェクト (C 関数が作る内部の Array が古いレジスタに残っていた) だけだった。
  形式を意味論の層で書いたことが効いた。
- **命令の差は無かった**。4.0 系と 4.1.0-rc2 の命令の表は同一で、運んだ 4.0 系の mrblib の
  命令列を SabiRuby がそのまま動かせた。差が出たのは `catch` の作り (C の bytecode の
  Proc か、native のループ枠か) のような、ライブラリの実装の違いだった。
- **古いレジスタが効く**。枠の窓の中に、もう使われない値が残っている。`builtin_patch` の像
  では、スタックの 7 番に `puts` などの C 関数が作った内部の Array (クラス欄が NULL) が
  残っていて、最初はこれのクラスが引けずに断っていた (素のクラスを当てて直した)。古い
  レジスタが SabiRuby に無い permanent を指していれば、プログラムが使わない値を理由に断る
  ことになる。試験の像ではそうなったものは無いが、起こりうる。
- `ci->blk` (枠の渡されたブロック) は SabiRuby には要らなかった。ブロックのレジスタに同じ
  ものがある。
- SabiRuby の Env は `ctx` (どの文脈のスタックか) を持つ。像はルートの文脈だけなので ROOT
  で足りた。

## 撤回した仮説

- 「SabiRuby 側に、C mruby の名前と SabiRuby の組み込みの対応表を作る」→ 名前を引く手順で
  足りた。表は gembox の違いのたびに作り直しになる。
- 「SabiRuby の `Integer#times` などに名前で結べば、pc の違いだけ直せば済む」→ 命令列が
  違うので、pc の対応は付かない。中身を運ぶしかない (計画の決めごとのとおり)。
- 「枠の `ci->blk` を SabiRuby の枠に写す欄が要る」→ 要らない (上)。
- 「mrblib の命令列を運んでも、4.1 の VM で意味が違う命令があるかもしれない」→ 試験の
  範囲では無かった。命令の表は同一。

## 残件 (逆向き SabiRuby → mruby で要りそうなこと)

- 書き出す点: SabiRuby の `exec_frames` の頭の判定 (task・step・GC) に印を相乗りさせる形が
  自然。C mruby の `task.switching` への相乗りと同じ考え方。
- 名前を付ける側: SabiRuby が自分の組み込みを C mruby と同じ手順でなめて名前を付ける
  (この段の「名前を引く」の逆)。SabiRuby の native の中には C mruby では Ruby のもの
  (`Kernel#puts` など) があり、その逆もある。枠がそこにあるときの扱いを決める。
- SabiRuby の native ループ枠 (`catch`・`sort { }`・`Array.new(n) { }` など。ブロックが自分の
  枠で動く) は、C mruby では C の関数の枠になる。逆向きでは、その中の save は断る場面になる
  (C mruby の「C の関数が呼んだブロックの中」と同じ)。
- 運ぶ irep: SabiRuby の mrblib (4.1.0-rc2 製) の命令列を C mruby (4.0 系) で動かすことになる。
  命令の表は同じなので動く見込みだが、確かめる。
- SabiRuby だけにあるもの (`Method::Closure`、Data の handle、HostStore) は C mruby に対応が
  無い。
- 古いレジスタの扱い: 生きているレジスタだけを書く (命令列の解析で決める) と、拒否が減り
  像も小さくなる。両方向で効く。

## 決めてほしいこと

1. mrblib の irep の中身を**常に**運ぶ (いまの実装) でよいか。像は mrblib の枠があるとき
   だけ数十〜数百バイト増える。
