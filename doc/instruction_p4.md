# 実装指示書 P4: Task と Fiber、形式 v1 (行番号つき)

`doc/plan.md`、`doc/format_v0.md`、`doc/report/p1.md`〜`p3.md` を先に読む。

## なぜ要るか (2026-11-03 ユーザ)

Family mruby は、アプリの本体を最初から mruby の Task として走らせる (C の側が
`mrc_create_task` で Task を作り、`mrb_task_run` でスケジューラを回す)。アプリも
自分で Task を作る (シェルの裏のジョブなど)。v0 は「Task・Fiber の中は断る」ので、
このままでは Family mruby のどのアプリも運べない。**Task は必須**、Fiber も同じ
仕組み (実行のコンテキストが複数ある) の延長で入れる。

## 判断の方針 (2026-11-03 ユーザ)

多少大変でも楽をせず、本質的な対応を選ぶ。断る・除外する・回避するより、正しく運べる
ように作る。断るのは、原理的に運べない物 (C のフレームなど) に限り、その理由を書く。

## 決まったこと・親の仮決め (ユーザがあとで見直す)

- 形式を **v1** にする (形が変わるので)。v0 の読み込みは残さなくてよい (外に読み込み側が
  いない)。SabiRuby のリーダーも v1 に追従させる。(決定)
- 行番号のデバッグ情報 (irep ごとの行の表) を v1 の任意のセクションとして入れる。復元後の
  バックトレースに行番号が出ること。P5 の可視化でも使う。(決定。P3 でセクション `DBG0` として
  入った。v1 ではこれを正式のセクションとして文書に書き、SabiRuby のリーダーと揃える)
- P3 で足したセクション (`GCS0`・`DBG0`・`END0`) と種類 (Struct・Set・Rational・Complex・bigint・
  Random・Time・Regexp・MatchData など) は v1 にそのまま引き継ぐ。
- **起きる時刻は「残りの tick」で運ぶ**。着いた先の今の tick に足して起きる時刻を
  決め直す。移動にかかった時間は待ちに含めない (同じイメージから何度復元しても同じ動きに
  なり、試験で再現できるため)。(親の仮決め)
- 走っていた Task の残りのタイムスライス (timeslice) は、着いた先で満タンから始める。
  (親の仮決め)
- アプリの本体の Task (C の側が作るもの) は、普通の Task と同じに運ぶ。復元の側では
  ドライバが Task を作り直し、スケジューラを回し直す。(親の仮決め)

## やること

1. **形式 v1** (`doc/format_v1.md` を新しく書く。v0 の文書は経過として残し、冒頭に
   「v1 で置き換えた」と書く):
   - **実行のコンテキストの表**: root と、Fiber・Task ごとのコンテキスト。それぞれにスタック・
     フレーム (v0 の §10 をコンテキストごとに)・状態。Fiber は状態 (未開始・実行中・
     中断中・終了) と resume の連なり (prev)。
   - **Task の表**: コンテキストへの参照、状態とどのキュー (dormant / ready / waiting /
     suspended) のどの順にいるか、優先度、名前、待ちの理由と中身 (sleep の残り tick、
     join 先の Task、Queue と残り tick)、戻り値、Task のオブジェクト。
   - **Task::Queue**: 中身と待っている Task の並び。
   - **デバッグ情報のセクション** (任意): irep ごとの行の表 (ファイル名と命令の位置 → 行)。
2. **mruby (C) 側**: 書き出しと復元を v1 に。セーフポイントが Task のコンテキストの中で来たときの
   扱い (今の判定は root 以外ではスケジューラへ戻る) を整理し、hook がスケジューラへ
   戻る前に呼ばれること。復元後はドライバがスケジューラを回し直す。
   - ドライバに **Family mruby と同じ起動の形** (`checkpoint run --as-task`:
     プログラムの本体を Task にして `mrb_task_run`) を足す。試験は両方の形で。
   - 時刻は試験で揺れないように、試験のビルドでは**仮想の時計** (tick を命令の数か
     スケジューラの回数で進める) を使えるようにする。普段のビルドは今の HAL のまま。
3. **SabiRuby 側** (worktree、`SABIRUBY_DIR` に渡すもの、ブランチ
   `feature/checkpoint`、feature `checkpoint`): v1 の読み込み、Fiber と Task の
   復元 (片道)。SabiRuby の Task・Fiber の作りとの違いは表にして report に。
4. **試験**:
   - サンプル: sleep で待つ Task が複数 (優先度で出力の順が決まる)、Queue の
     生産者と消費者、join、`Task#suspend` / `resume`、Task の中の `save`、
     Fiber の生成器 (Enumerator 相当)、入れ子の resume、Task の中の Fiber。
     どれも、Task が待っている最中・走っている最中の両方で止める。
   - P3 の外からの停止 (`rake fuzz`、`tools/fuzz.rb`) を、mruby-task と mruby-fiber の
     試験一式にも広げる。P3 の断った理由のうち「Fiber を値として持つ」「Fiber・Task の中で
     要求した」「Task がある」「Task::Queue」「要求したあとで Fiber に入った」(合わせて約 1.9 万点、
     `doc/report/p3.md`) が、原理的に運べないもの以外 0 になることを数字で示す。残るものは
     理由を書く。
   - P3 と同じ規模の長い版 (20 の種) を流し、食い違い 0 を保つ。
   - 64 ⇔ 32、別のプロセス、`--as-task` の有無、SabiRuby への片道。
   - `rake test`、ASan、GC_STRESS が通ること。
5. **行番号**: 復元後に例外を起こし、バックトレースの行番号が往復なしと一致すること。

## 触ってよい範囲・止まる条件・守ること

- P3 の指示書と同じ (判断の方針も同じ)。加えて: mruby-task のスケジューラの作り (キュー・優先度の決め方) を
  変える必要が出たら止まる。
- 普段のビルドの `vm.c` の patch を変えたら、valgrind の命令数で前後を比べる。
- report は `doc/report/p4.md`: v1 で足したもの、Task・Fiber の運び方、仮決めの
  妥当さ (実装してみて困った所)、試験の数字、SabiRuby との違い、残件 (P5 で
  見せるのに要る情報)。
